Git 병합 충돌 검사 다음에 DB 테스트를 한 이유

작업 트리를 바꾸지 않는 병합 검사와, 실제 병합 뒤 스키마 제약까지 확인하는 DB 테스트를 구분했습니다.

우동균·2026.10.28
글 수정

진행 중인 작업을 바꾸지 않고 기준 브랜치와 충돌할지 미리 보고 싶을 때 git merge-tree --write-tree HEAD origin/develop를 사용했습니다. 작업 트리와 인덱스를 그대로 두고 두 커밋을 병합한 결과를 확인할 수 있습니다. 한 브랜치에서는 기준 브랜치에 새 커밋이 23개 들어왔을 때 검사에 충돌이 없었습니다. 이후 다른 변경이 먼저 병합되자 다시 실행한 검사에서 문서 충돌이 나타났고, 기준 브랜치를 실제로 합쳐 그 파일을 정리했습니다. 미리 본 결과는 그때 비교한 두 커밋에 대한 것이었습니다.

SQL 파일과 테스트 데이터가 함께 바뀌는 경우

연습 시간 통계 작업에서는 기준 브랜치를 합칠 때 Git이 멈추지 않았지만, DB 검사에서 FAILED 상태의 연습 세션을 만들던 픽스처가 실패했습니다. 기준 브랜치의 마이그레이션이 실패 상태에 실패 사유가 있어야 한다는 제약을 추가했기 때문입니다. 스키마와 통계 테스트가 서로 다른 파일에 있어서 Git은 두 변경을 그대로 합칠 수 있었습니다.

통계가 실패한 세션을 제외하는지 확인하려면 FAILED 행은 필요했습니다. 그래서 픽스처에 NO_SOUND를 넣어 새 스키마를 만족하면서도 같은 통계 조건을 검사하도록 고쳤습니다. 새 임시 MySQL에서 다시 실행한 기록에는 기본 테스트 133개와 DB 테스트 30개가 통과한 것으로 남았습니다.

병합을 미리 보는 명령은 비교할 커밋을 정하고 충돌 파일을 찾는 데 썼습니다. 데이터와 코드를 같이 해석해야 하는 변경은 합친 뒤 실제 마이그레이션을 적용한 DB에서 검사했습니다. 통계 동작을 지키면서 픽스처가 새 제약을 만족하는지는 두 번째 확인에서 드러났습니다.
