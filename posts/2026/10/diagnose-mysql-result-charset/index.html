MySQL 한글이 물음표로 보일 때

MySQL 조회에서 보이는 물음표가 저장된 값인지, 결과를 내보내는 연결에서 생긴 것인지 나눠 봅니다.

우동균·2026.10.29
글 수정

곡 제목을 MySQL 클라이언트에서 읽을 때, 일부 한글이 ??? 또는 ?????로 표시됐습니다. 화면만 보고 저장값을 고치면 멀쩡한 행까지 바꿀 수 있습니다. 이 기록에서 확인한 것은 조회 화면에 물음표가 있었다는 사실입니다. 저장된 바이트에 물음표가 있었는지는 별도의 확인이 필요했습니다.

표시와 저장값 분리

MySQL은 연결에서 사용하는 문자 집합에 맞춰 결과를 변환할 수 있습니다. 클라이언트가 요청한 결과 문자 집합으로 한글을 표현하지 못하면 저장값이 정상이어도 화면에는 물음표가 나올 수 있습니다. 먼저 같은 행을 utf8mb4를 지정한 세션에서 다시 읽고, 연결이 실제로 어떤 문자 집합을 쓰는지 확인하는 방식이 있습니다. MySQL 연결 문자 집합 문서

SELECT @@character_set_client, @@character_set_connection, @@character_set_results;
SELECT title, HEX(title) FROM songs WHERE id = 1;

두 번째 쿼리의 테이블과 ID는 예시입니다. MySQL CLI는 --default-character-set=utf8mb4를 지정해 다시 연결할 수 있습니다. HEX(title)은 결과를 ASCII로 표현하므로, 값에 들어 있는 바이트를 표시용 문자 변환과 분리해 볼 수 있습니다. 컬럼이 UTF-8이라면 의심한 위치에 유효한 한글 바이트가 있는지, 실제로 3F가 반복되는지 확인합니다.

조회 결과별 진단

한글 바이트가 남아 있고 새 세션에서 정상으로 읽히면 결과 문자 집합 쪽으로 범위를 좁힐 수 있습니다. 두 세션의 결과가 같고 저장값에 3F가 들어 있다면 가져오기나 저장 시점에 어떤 인코딩을 썼는지 추적합니다. 컬럼과 연결이 모두 UTF-8이어도 터미널 표시가 깨진다면 같은 결과를 다른 출력 환경에서 읽어 볼 수 있습니다.

당시 확인한 것은 조회 화면에 물음표가 나타난 일입니다. 원인을 확인하려면 같은 행을 기존 세션과 utf8mb4 세션에서 각각 읽고, 두 세션의 결과 문자 집합과 HEX(title)을 나란히 남겨야 합니다. 기록에는 이 재조회와 바이트 대조 결과가 없어, 문제가 저장값에 있었는지 출력에서 생겼는지는 열어 둡니다.
