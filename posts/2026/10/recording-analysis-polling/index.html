녹음 업로드 202 이후 앱이 기다리는 것

녹음 접수와 평가 완료를 분리하고, 앱이 2초마다 상태를 묻다가 멈추는 조건을 가짜 시계로 확인했습니다.

우동균·2026.10.29
글 수정

얼쑤에서 연주 녹음을 보낸 사용자는 평가 화면을 기다립니다. 앱 입장에서는 파일을 서버에 전달했는지, 평가를 받을 수 있는지 두 가지를 확인해야 합니다. 둘을 한 요청에서 처리하면 파일을 저장한 뒤에도 분석이 끝날 때까지 업로드 연결을 유지해야 합니다. 저는 녹음을 접수한 뒤 202 Accepted로 답하고, 앱이 같은 연습 세션의 상태를 따로 조회하도록 연결했습니다. RFC 9110의 202 Accepted

서버의 접수 시점

백엔드는 앱이 보낸 파일을 검사해 R2에 원본을 저장합니다. DB에는 원본 키와 녹음 정보를 기록하고 세션을 PENDING으로 바꿉니다. DB 커밋을 확인한 이벤트 리스너가 그 세션을 백그라운드 실행기에 넘깁니다. 분석 작업은 세션을 읽고, 분석 서버는 백엔드가 전달한 서명 URL로 원본을 가져갑니다. 업로드 응답은 실행기에 작업을 넘긴 뒤 분석 결과를 기다리지 않고 돌아옵니다.

앱 → 백엔드에 녹음 업로드 → R2에 원본 저장 → DB에 PENDING 기록·커밋
                                            ├─ 실행기에 분석 제출 → 202 응답
                                            └─ 백그라운드 분석 → DB에 DONE 또는 FAILED 기록
앱 → 같은 연습 세션의 상태 조회 → DONE이면 별도로 평가 조회

커밋 뒤에 작업을 넘긴 데는 이유가 있습니다. 실행기는 별도 DB 연결에서 세션을 읽습니다. 먼저 실행하면 아직 커밋하지 않은 PENDING 상태나 원본 키를 볼 수 없어 분석을 시작할 근거를 놓칠 수 있습니다. 실패한 분석을 다시 시작할 때도 새 시도 정보를 DB에 반영한 뒤 같은 실행기에 넘깁니다.

2초마다 조회하고 끊긴 시간 측정

대기 화면이 열려 있으면 접수 직후 같은 세션을 한 번 조회합니다. PENDING을 받으면 그 응답에서 2초 뒤 다시 묻습니다. DONE이면 조회를 끝내고 평가를 요청합니다. FAILED도 조회를 끝내고, 응답에 담긴 실패 사유에 맞는 화면을 보여줍니다. 다른 화면에 있거나 앱이 백그라운드로 가면 조회를 멈춥니다. 분석이 진행 중이었다면 대기 화면으로 돌아올 때 바로 한 번 더 묻습니다.

PENDING이 돌아올 때마다 앱은 마지막 상태 응답 시각을 갱신합니다. 연결 오류 등으로 읽을 수 있는 상태 응답을 70초 동안 받지 못하면 앱에서 시간 초과 화면을 띄웁니다. 서버는 자체 시계로 분석 시도의 마감을 판단하므로 앱이 시간 초과를 표시한 사이에도 결과를 저장할 수 있습니다.

사용자가 이 화면에서 다시 시도했을 때 서버가 이미 분석 중이라면, 새 시도를 만들지 않고 같은 202를 돌려줍니다. 서버 API와 DB를 함께 사용한 테스트에서 시도 번호가 그대로였고 실행기에 추가된 작업은 0건이었습니다. 앱은 202를 받으면 기존 세션의 상태를 다시 조회합니다. 재시도 요청이 409를 받아도 같은 세션을 다시 읽습니다. 예를 들어 앱이 통신을 못 하던 사이 서버가 DONE을 기록했다면 결과 화면으로 갈 수 있습니다. 같은 녹음을 다시 분석해도 결과가 뒤섞이지 않게

가상 시계로 경계 검증

Kotlin Multiplatform 공통 테스트에 가짜 시계와 응답 대역을 넣었습니다. 서버 응답 순서와 시각을 정해 놓고 대기 화면이 몇 번 조회하는지, 어떤 상태에서 멈추는지 확인했습니다.

테스트 조건확인한 앱 동작
첫 두 번은 PENDING, 세 번째는 DONE시작 즉시, 2초, 4초에 각각 한 번 조회했습니다. 평가 ID를 받은 뒤 시계를 10초 더 움직여도 총 조회는 3회였습니다.
첫 응답이 FAILED응답의 실패 사유를 앱 상태에 기록했고 10초를 더 움직여도 조회는 첫 1회에 그쳤습니다.
시작 뒤 상태 조회가 계속 실패69,999ms에는 실패 상태가 비어 있었고 70,000ms에 앱의 시간 초과 상태가 됐습니다.
첫 조회 후 앱을 백그라운드에 5분 둠조회 횟수는 1회로 유지됐습니다. 복귀 직후 한 번, PENDING 응답 2초 뒤 한 번 더 조회했습니다.

표의 시간은 테스트에서 움직인 시계 값입니다. 별도로 배포 서버에 1.45초짜리 합성 AAC 한 건을 올려 장애 복구를 확인했습니다. 분석 서버를 복구한 직후 첫 재시도는 다시 실패했고, 같은 세션을 한 번 더 재시도하자 접수 후 약 15.54초에 DONE을 확인했습니다. API 응답과 DB의 평가 저장 기록, 분석 로그가 일치했습니다. 실제 iPhone에서는 마이크를 허용해 녹음하고 평가 화면에 도달하는 흐름을 별도로 확인했습니다. 이렇게 앱 테스트는 조회·중단의 경계를, 서버 점검은 실패 뒤 평가가 저장되는 경로를, 실기기 관찰은 마이크 입력부터 평가 화면까지의 흐름을 확인했습니다.
