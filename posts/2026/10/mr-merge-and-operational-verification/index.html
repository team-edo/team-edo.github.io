MR 병합 뒤에도 운영 확인이 남았다

병합 직후 완료로 표시됐지만 운영에서는 404였던 약관 API를 계기로, 작업 상태와 실제 완료 조건을 따로 확인한 사례입니다.

새 약관 API를 운영에서 호출해 HTTP 200을 받는 것이 한 작업의 완료 조건이었습니다. MR이 병합되자 Jira는 작업을 완료로 표시했지만, 같은 시점에 운영 API는 404를 반환했습니다.

자동 종료 대상과 운영 응답 확인

저희 프로젝트는 MR이 병합되면 연결된 작업을 완료로 전환했습니다. 약관 사례에서는 배포 이력과 운영 응답을 계속 확인해 새 버전의 200 응답까지 기록했습니다. 배포가 막힌 원인과 복구 과정은 별도 글에 정리했습니다. 인증 추가 뒤 자동 배포가 10번 실패한 이유

반대로 문서 참조만 고친 MR에서는 다른 작업에 남은 실기기 확인을 유지해야 했습니다. 이 프로젝트에서는 닫는 문구가 없어도 제목이나 본문에 전체 작업 키가 들어가면 자동화의 대상이 될 수 있었습니다. 문서 MR에는 계속 진행할 작업의 전체 키가 들어가지 않도록 참조 표기를 정리했고, 병합 뒤 실기기 점검 작업을 다시 읽어 진행 중임을 확인했습니다. 확인 범위는 당시 프로젝트의 자동화와 그 작업의 상태입니다.

메일은 받은편지함까지 확인했습니다

인증 메일을 켜는 작업에서는 SMTP 설정을 백엔드에 전달했습니다. 처음 확인했을 때는 앞선 배포 검사가 연속으로 실패해 새 버전이 운영에 반영되지 않았습니다. 배포 검사 수정과 새 버전 반영을 확인한 뒤, 검증용 주소로 가입 인증 요청을 한 번 보냈습니다.

받은편지함수신자에게 같은 요청의 메일이 도착했음을 확인했습니다.

수신까지 확인한 범위

HTTP 202가 답하는 것은 요청 접수까지입니다. 메일 도착이 완료 조건인 이 작업에서는 수신 확인을 별도로 남긴 뒤 상태를 직접 완료로 바꿨습니다. 한 건의 요청으로 확인한 결과이며, 인증번호를 제출하는 가입 절차와 다른 제공자의 배달 성공률은 이 기록의 범위 밖입니다. HTTP 202의 의미

MR 종료 문구를 다시 확인하는 법

한 MR에서 미리 입력한 설명 아래에 양식이 닫는 문구를 더 붙였습니다. 편집 화면에서 같은 참조가 두 줄이었고, 텍스트 편집 모드로 설명을 다시 넣어 한 줄로 맞췄습니다. 이때 남은 기록은 편집 화면의 문구까지입니다. 저장된 설명을 다시 읽는 절차를 두면 편집 과정에서 추가된 종료 참조도 발견할 수 있습니다. MR을 API로 만드는 흐름이라면 생성 응답 뒤에 같은 MR을 다시 조회하는 방식으로도 이 확인을 할 수 있습니다. GitLab MR 조회 문서

운영 완료를 확인할 때는 병합과 작업 상태, 실행 중인 버전, 사용자가 받은 결과를 순서대로 기록했습니다. 약관에서는 새 버전의 API 응답이 마지막 확인이었고, 인증 메일에서는 수신자 확인이 마지막이었습니다.
