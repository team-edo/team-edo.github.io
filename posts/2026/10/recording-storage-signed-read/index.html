녹음 저장소를 다시 고르면서 15분 읽기 계약을 유지한 이유

구현 전에 녹음 저장소를 GCS에서 R2로 다시 골랐습니다. 분석 서버에 주는 15분 읽기 권한은 그대로 두고 실제 만료와 삭제를 확인했습니다.

우동균·2026.10.27
글 수정

얼쑤에서 연습 녹음을 받으면 백엔드는 원본을 객체 저장소에 보관하고, 분석 서버는 필요한 파일을 가져와 처리합니다. 처음에는 서울 리전과 신규 계정 크레딧을 고려해 Google Cloud Storage(GCS)를 쓰는 설계를 잡았습니다. 다음 날에는 크레딧이 끝난 뒤의 비용과 다운로드 조건, 저장소를 바꿀 때의 구현 부담을 다시 검토해 S3 호환 API를 쓰는 Cloudflare R2로 계획을 바꿨습니다.

분석 서버에는 15분 동안 한 파일을 읽을 권한만 준다

분석 서버가 해야 할 일은 전달받은 녹음 한 건을 읽는 일이었습니다. 그래서 백엔드가 특정 객체에 대해 GET 요청만 15분(900초) 동안 허용하는 URL을 서명하고, 분석 서버는 그 주소로 원본을 내려받도록 했습니다. 저장소의 자격 증명은 서명하는 백엔드에만 둡니다. 유효한 URL을 가진 사람도 파일을 읽을 수 있으므로 주소 자체를 노출하지 않는 것도 이 설계의 일부입니다. Google Cloud Storage 서명 URL · Cloudflare R2 서명 URL

GCS와 R2에서 주소를 만드는 방법은 다르지만 분석 서버에 넘기는 것은 어느 쪽이든 만료 시간이 있는 읽기용 URL입니다. 저장소 선택을 바꾸면서 백엔드의 서명 구현을 바꿀 수 있었고, 분석 서버가 녹음을 받는 인터페이스는 유지했습니다. GCS는 초기 설계안이었고, 구현과 아래 검증은 R2에서 진행했습니다.

같은 객체에 새 주소를 발급해 만료와 삭제를 구분했다

배포한 백엔드의 저장소 구현으로 검증용 합성 객체를 썼습니다. 서명 주소가 열린다는 사실만 확인하면, 시간이 지나 권한이 실제로 끝나는지 알 수 없습니다. 반대로 만료 주소 한 건이 실패하는 것만 보면 파일이 삭제돼서 실패했을 수도 있습니다. 그래서 같은 객체에 새 서명을 발급해 대조했습니다.

확인한 조건실제 응답
발급 직후 900초짜리 서명으로 읽기HTTP 200, 원본 바이트와 응답 본문 일치
발급한 지 900초가 지난 주소로 읽기HTTP 403 ExpiredRequest
같은 객체에 새 서명을 발급해 읽기HTTP 200, 원본 바이트와 응답 본문 일치
객체를 삭제한 뒤 방금 성공한 주소로 읽고 별도로 HEAD 요청두 요청 모두 HTTP 404

만료 직후 새 주소는 같은 바이트를 돌려줬으므로 이전 주소의 실패를 객체 삭제와 구분할 수 있었습니다. 이어서 객체를 지운 뒤에는 방금 성공했던 주소도 404가 됐습니다. 저장소를 바꾸는 설계 판단은 구현 전에 했고, 읽기 권한이 만료되는 시점과 원본이 사라진 뒤의 응답은 R2에서 실제 요청으로 확인했습니다.
