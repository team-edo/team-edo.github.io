분석 API의 오류 응답과 로그에서 서명 URL을 숨긴 과정

필수 필드가 빠졌을 때 요청 전체가 오류 응답에 들어가는 문제와 HTTP 클라이언트의 URL 로그를 막고, 실제 HTTP 요청과 회귀 테스트로 확인했습니다.

우동균·2026.10.28

얼쑤의 분석 서버는 요청에 담긴 서명 URL로 녹음을 내려받습니다. URL에 읽기 권한이 담겨 있어 유효 시간 안에는 주소만으로 파일을 요청할 수 있습니다. 분석 API를 구현할 때 이 주소가 어디에 남는지 점검했습니다. 제가 작성한 코드에서 URL을 로그에 쓰지 않아도 두 곳에 남을 수 있었습니다. 요청을 검증하는 프레임워크의 응답과 녹음을 내려받는 HTTP 라이브러리의 로그입니다.

BPM을 틀리게 보냈을 때는 문제가 드러나지 않았다

당시 FastAPI 기본 검증 응답은 HTTP 422와 함께 오류가 난 입력값을 input에 넣었습니다. bpm에 0을 보내면 오류의 입력값도 0이었습니다. 이 경우만 검사하면 기존 처리기를 써도 서명 URL이 응답에 없었습니다. bpm을 아예 빼자 검증기가 그 필드가 있어야 할 요청 객체를 오류에 담았습니다. 같은 객체의 audioUrl도 응답에 실릴 수 있었습니다.

RequestValidationError 처리기를 등록해 오류마다 필드 위치와 오류 종류만 보내도록 바꿨습니다. 호출자는 어떤 값을 빠뜨렸는지 알 수 있고, 응답에 원본 요청이 복사되지 않습니다. 회귀 테스트도 잘못된 숫자를 주는 경우에서 필드를 누락하는 경우로 바꿨습니다.

다운로드를 실제로 거쳐야 보이는 로그

HTTPX는 INFO에서 요청 메서드와 URL 전체를 기록했습니다. 주소에 붙은 서명도 함께 남았습니다. 다운로드 함수의 결과만 가짜로 돌려주는 테스트는 HTTPX를 호출하지 않으므로 이 문제를 잡을 수 없었습니다. 앱의 루트 로그를 DEBUG로 열어도 이 요청 줄이 나오지 않도록 HTTPX와 httpcore 로거의 수준을 WARNING으로 지정했습니다.

예외도 따로 확인했습니다. 예상한 다운로드 실패는 URL을 빼고 고정된 502 오류로 돌려줍니다. 분석 중 예상 밖의 예외는 요청 처리 경계에서 받아 정해진 500 본문을 반환합니다. 그때 로그에는 예외의 종류와 세션 번호, 시도 번호, 처리 시간을 남겼습니다. 원인을 좁힐 단서는 유지하면서 예외 메시지에 섞인 주소가 함께 기록되는 길을 닫았습니다.

응답과 로그를 따로 대조했다

로컬에서 실제 분석 API를 띄우고 저장소 자리에 별도 HTTP 서버를 놓았습니다. 합성 M4A, 없는 파일, 필수 필드를 뺀 요청을 각각 보내 응답을 확인하고, 캡처한 DEBUG 로그에서 테스트용 서명 토큰을 찾았습니다.

기존 실행 검증에서 보낸 요청관측한 응답
저장소 대역의 합성 M4AHTTP 200, 분석 완료
저장소 대역에 없는 파일HTTP 502
bpm을 뺀 요청HTTP 422, 원본 입력 필드 없음

이 실행에서 DEBUG 로그에 테스트용 서명 토큰이 나온 횟수는 0회였습니다. 자동 검사에서는 URL이 들어 있는 예외를 일부러 던져 상태 코드와 함께 500 본문이 정해진 값인지 확인했습니다. 422 처리기를 제거하거나 HTTPX의 INFO 로그를 다시 허용했을 때는 해당 회귀 테스트가 실패했습니다. 검사한 범위는 이 로컬 실행과 자동 테스트가 거친 응답·로그 경로입니다.
