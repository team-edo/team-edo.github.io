메시지에서 지운 파일 경로가 예외에 남은 이유

디코더 오류에는 stderr와 실행 인자가 남을 수 있습니다. 메시지를 정리하고 시간 초과의 원래 예외가 연결에도 남지 않는지 확인했습니다.

녹음 분석 서버는 내려받은 파일을 FFmpeg에 넘겨 PCM으로 변환합니다. 손상된 녹음을 디코딩하지 못하면 파일 문제를 알리는 오류를 반환하고, 시간 초과처럼 도구 실행 자체가 실패하면 별도로 처리합니다. 두 경로를 정리하면서 오류를 어디서 읽든 입력 파일의 위치가 드러나지 않게 하려 했습니다.

표준 오류와 예외 연결의 경로 노출

FFmpeg가 쓴 stderr에는 실행에 넘긴 파일 이름이 포함될 수 있습니다. 디코딩 실패를 설명하는 메시지를 만들 때 해당 위치를 <input>으로 치환했습니다.

시간 초과는 다른 경로를 탑니다. Python의 subprocess.TimeoutExpired에는 실행 인자가 들어 있습니다. 이 예외를 처리하는 도중 새 예외를 올리면, 화면에 표시하는 메시지에서 파일 위치를 빼도 원래 예외 객체가 __context__에 남을 수 있습니다. raise ... from None은 기본 traceback에서 그 연결을 감추지만, 객체에서 __context__를 제거하지는 않습니다. Python의 예외 연결 문서

예외 처리 블록 밖에서 새 오류 생성

디코더에서는 시간 초과를 잡고 해당 처리 블록을 빠져나간 뒤, 제한 시간만 담은 새 오류를 올리도록 했습니다. 이 경로에서는 원래 실행 명령을 새 예외의 명시적 원인으로 연결하지 않습니다.

테스트에는 구분하기 쉬운 표식을 이름에 넣은 디렉터리 아래 파일을 준비했습니다. 손상된 녹음의 예외 메시지에서 표식이 나오지 않는지 확인합니다. 별도로 실행 제한을 짧게 주어 시간 초과를 일으킨 뒤에는 메시지뿐 아니라 __context__와 __cause__도 비어 있는지 검사합니다. 응답 문자열 검사와 예외 연결 검사는 서로 다른 노출 경로를 확인합니다. 테스트가 다루는 범위는 이 디코더의 오류이며, 서비스의 모든 로그 경로를 포괄하는 검사는 아닙니다.
