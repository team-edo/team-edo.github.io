인증 메일, HTTP 202에서 받은편지함까지

운영 백엔드에 SMTP 설정을 연결한 뒤 인증 메일을 한 통 보냈습니다. HTTP 응답, 발송 로그, 수신자 확인이 각각 무엇을 말하는지 나눠 기록했습니다.

우동균·2026.10.28
이 글의 목차
  • 발송 요청 한 건을 끝까지 추적
  • 수신까지 확인한 범위

가입 인증 메일을 운영 환경에서 켜려면 백엔드 컨테이너가 SMTP 설정을 받아야 했습니다. 배포 구성을 수정해 인증 메일에 필요한 설정을 백엔드에 전달했습니다. 이 변경의 검증에는 서버가 뜨는 것보다 한 단계가 더 필요했습니다. 메일이 사용자에게 도착하는지 보는 일이었습니다.

처음 운영을 확인할 때는 자동 배포가 연속으로 실패하고 있었습니다. 설정 전달이나 메일 발송을 판단하려면 확인할 버전이 먼저 운영에 올라가 있어야 했습니다. 실패한 단계와 운영에 반영되지 않은 변경을 팀에 공유하고, 배포 검사가 고쳐진 뒤 수신 검증을 다시 진행했습니다.

발송 요청 한 건을 끝까지 추적

검증에 쓰기로 한 주소로 가입 인증 요청을 한 번 보냈습니다. API는 HTTP 202를 반환했고, 백엔드 로그에서 그 요청의 발송 오류는 발견되지 않았습니다. 202는 요청이 받아들여졌다는 응답입니다. 받은편지함에 들어갔는지는 HTTP 응답만으로 알 수 없었습니다. HTTP 202의 의미

마지막으로 수신자에게 메일 도착을 확인했습니다. 같은 요청에 대해 서버 응답, 발송 오류 유무, 수신 결과를 따로 적었습니다. 검증 기록에는 주소나 인증번호를 남기지 않았습니다.

수신까지 확인한 범위

한 건의 요청에서 설정 전달부터 수신까지 경로가 이어졌습니다. 인증번호를 제출해 가입을 끝내는 과정이나 다른 메일 제공자의 배달 성공률은 이 검증에 포함하지 않았습니다. 외부로 실제 메시지가 나가는 기능에서 성공 응답과 상대방이 받은 결과를 구분하면, 적은 검증 요청으로도 어느 단계까지 확인했는지 분명하게 남길 수 있습니다.
