오류 안내가 스스로 사라진 이유

편집을 막는 검증은 동작했지만 Snackbar가 보이지 않던 문제에서, 효과의 키와 메시지 소비 순서를 확인한 과정을 정리했습니다.

박찬형·2026.11.13
이 글의 목차
  • 한 상태값이 작업의 시작과 취소를 모두 결정했다
  • 표시가 끝난 뒤 소비하도록 순서를 바꿨다
  • 메시지가 있다는 검사와 안내가 보인다는 검사를 나눴다

악보 편집기에서 칸을 바꾸는 버튼을 눌렀는데 아무 일도 일어나지 않았습니다. 구간 빠르기가 지정된 악보에서 허용하지 않는 구조 변경이어서, 편집을 막는 동작 자체는 맞았습니다. 문제는 왜 막혔는지 알려 주는 안내도 보이지 않았다는 점입니다.

검증 분기에서는 메시지를 만들고 있었습니다. 화면의 입력과 초안도 남아 있었습니다. 빠진 것은 메시지가 만들어진 뒤 사용자가 읽을 수 있을 때까지의 과정이었습니다.

한 상태값이 작업의 시작과 취소를 모두 결정했다

화면은 메시지가 생기면 LaunchedEffect에서 Snackbar를 표시했습니다. 같은 메시지를 효과의 키로 사용하면서, 표시를 기다리기 전에 ‘소비했음’으로 처리했습니다. 원인을 보여주기 위해 줄이면 다음 순서입니다.

LaunchedEffect(message) {
    val text = message ?: return@LaunchedEffect
    consumeMessage() // message를 null로 바꾼다
    snackbarHostState.showSnackbar(text)
}

text에 문자열을 복사해 뒀으니 표시할 내용은 남아 있습니다. 하지만 코루틴의 수명은 그 지역 변수와 별개였습니다. 메시지를 소비하면 다음 재구성에서 효과의 키가 바뀝니다. 기존 키로 실행 중인 효과가 취소될 수 있습니다.

Compose의 LaunchedEffect는 키가 달라지면 기존 코루틴을 취소하고 새 효과를 시작합니다. 이는 공식 효과 수명주기 설명의 동작입니다.

여기에 showSnackbar의 동작이 겹쳤습니다. 이 함수는 안내가 사라질 때까지 중단하며, 호출 코루틴이 취소되면 표시 중이거나 대기 중인 Snackbar도 제거됩니다. SnackbarHostState API 문서

메시지 생성 → 효과 시작 → 메시지 소비
                           ↓
                       효과의 키 변경
                           ↓
                  표시 중이거나 대기 중인 안내 취소

메시지 상태를 빨리 비워 중복 표시를 막으려던 순서가, 바로 그 메시지를 보여 주는 작업을 끝낼 수 있었습니다. 안내가 잠깐 나왔다 사라지거나 읽기 전에 끝나는 현상을 상태값 검사만으로는 잡기 어려웠습니다.

표시가 끝난 뒤 소비하도록 순서를 바꿨다

해당 편집 경로에서는 Snackbar 표시 작업이 끝난 뒤 메시지를 소비하도록 바꿨습니다. 같은 축약 예시에서 바뀐 부분은 두 줄의 순서입니다.

LaunchedEffect(message) {
    val text = message ?: return@LaunchedEffect
    snackbarHostState.showSnackbar(text)
    consumeMessage()
}

이제 메시지 소비가 진행 중인 표시 작업의 키를 먼저 바꾸지 않습니다. 안내를 보여 주는 동안 입력과 초안을 유지하고, 사용자가 내용을 고친 뒤 다시 시도할 수 있게 했습니다. 다른 메시지 표시가 있는 경우에는 기존 Snackbar를 닫는 처리도 해당 Route 안에서 유지했습니다.

이 예시는 한 메시지의 표시·소비 순서를 설명하는 코드입니다. 여러 이벤트를 빠르게 연속 전달해야 하는 화면이라면 메시지 식별자, 대기 정책과 화면 이탈 시 처리를 별도로 정해야 합니다. 모든 안내 경로에 두 줄의 순서만 적용하면 이벤트 전달 문제가 끝난다는 뜻은 아닙니다.

메시지가 있다는 검사와 안내가 보인다는 검사를 나눴다

수정 확인은 처음 문제가 나온 거절 동작으로 돌아가서 했습니다. 구간 빠르기가 있는 악보에서 금지된 칸 편집을 누르고, 변경이 차단되는지와 함께 이유가 실제 화면에 표시되는지 확인했습니다.

Android 에뮬레이터의 320×568dp 화면, 글꼴 배율 100%·130% 조건을 사용했습니다. 로컬 고정 API fixture로 공유 화면의 동작을 확인했으며 실기기·iOS·운영 배포를 검증한 결과로 쓰지는 않았습니다.

확인 지점답하려는 질문
검증 분기와 메시지 상태금지 동작을 감지하고 이유를 만들었는가?
효과의 키와 소비 순서표시 작업이 끝나기 전에 스스로 취소되는가?
실제 작은 화면의 거절 흐름사용자가 이유를 읽고 입력을 고쳐 다시 시도할 수 있는가?

상태값이 맞다는 증거가 화면 표시의 증거까지 대신하지는 못했습니다. 비슷한 안내가 사라지면 메시지를 만드는 함수 다음으로, 그 메시지가 어떤 효과를 시작하고 언제 그 효과의 키를 바꾸는지부터 확인할 수 있습니다.
