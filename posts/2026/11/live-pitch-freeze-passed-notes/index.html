지나간 음이 한꺼번에 틀림으로 바뀌던 실시간 채점

서버 채점 규칙을 실시간 판정에 옮기자 지나간 음의 색이 한꺼번에 뒤집혔습니다. 지나간 음의 색을 고정하고 조율 추정을 안정시킨 과정을 정리했습니다.

이 글은 앞서 쓴 「계산은 되는데 보이지 않던 실시간 채점」의 후속입니다. 그 글에서는 AI 연주 평가 중 실시간 음높이 판정이 계산만 되고 화면에 보이지 않던 이유를 확인했습니다. 실시간 판정과 서버의 최종 채점이 왜 다른지도 정리했습니다. 이번에는 그 판정을 악보에 칠하면서 겪은 문제를 다룹니다. 서버 규칙을 그대로 옮겼더니, 이미 지나간 음의 색이 한꺼번에 틀림으로 바뀌었습니다.

구현은 AI 코딩 에이전트와 함께 했습니다. 저는 표시 방식을 정하고 실기기에서 확인했습니다.

악보 칸에 색을 칠하기까지

평가 연주 중 정간보의 음 자리를 판정에 따라 칠하기로 했습니다. 맞는 음은 연두, 다른 음은 음정 오류 색, 측정 오류로 보여 판단을 보류한 음은 회색 테두리입니다. 쉼표와 꾸밈음은 칠하지 않습니다. 이 표시는 점수가 아니라 다른 음을 불었는지 알려 주는 안내입니다.

처음 버전은 그 순간의 판정만 보여 줬습니다. 실기기에서 써 보니 색이 남지 않아서, 음마다 판정 결과를 모아 지나간 칸에도 색을 남기도록 바꿨습니다.

그다음에 문제가 하나 더 보였습니다. 연주 중에 칠해진 틀린 칸과, 연주가 끝난 뒤 결과 화면의 틀린 칸이 달랐습니다. 실시간 판정은 그 순간의 높이만 보고, 서버는 녹음 전체로 조율 차이를 잰 뒤 뺍니다. 그래서 실시간 판정도 서버의 음정 규칙을 따르게 바꿨습니다.

서버 규칙을 그대로 옮기다

서버가 음정을 판정하는 순서를 실시간 쪽에 옮겼습니다.

단계내용
음의 값그 음에 들어온 값 중 앞뒤 20%를 버린 가운데 60%의 중앙값 오차(센트)
조율 차이지금까지 분 음들의 오차 중앙값을 악기의 조율 차이로 보고 뺌
보정 상한반음 이웃이 있는 곡은 40센트, 없으면 100센트. 넘으면 보정하지 않음
판정조율 차이를 뺀 오차가 ±50센트를 넘으면 다른 음. 옥타브가 달라도 다른 음

서버와 완전히 같지는 않습니다. 서버는 녹음 전체를 악보에 맞춰 정렬한 뒤 판정합니다. 실시간은 악보 시계로 소리를 음에 붙이므로, 빠르기가 어긋나면 앞뒤 음 소리가 섞일 수 있습니다.

각을 지나자 앞 음이 전부 틀림이 됐다

Galaxy S10(Android 12)에 설치하고 평가 연주를 했습니다. 부는 동안에는 맞음으로 칠해지던 음들이, 각을 지나고 나니 앞 음 전체가 틀림으로 바뀌었습니다.

서버에서는 생기지 않는 문제입니다. 서버는 녹음이 다 끝난 뒤 조율 차이를 한 번만 정합니다. 실시간에서는 음이 하나 들어올 때마다 조율 차이 추정이 다시 계산됩니다. 모든 음이 이 값 하나를 함께 쓰므로, 값이 바뀌면 이미 지나간 음까지 다시 판정됩니다.

가장 크게 흔들리는 지점은 보정 상한이었습니다. 추정값이 상한 안쪽이면 그만큼 빼 주고, 상한을 넘으면 서서히 줄지 않고 바로 0이 됩니다.

internal fun livePitchTuningOffset(noteErrors: Collection<Double>, maxTuning: Double): Double {
    val offset = median(noteErrors.filter { abs(it) <= LivePitchTuningOutlierCents }) ?: return 0.0
    return if (abs(offset) > maxTuning) 0.0 else offset
}

악기가 전체적으로 낮게 불리는 상태라면, 보정 덕에 맞음이던 음들이 보정이 꺼지는 순간 동시에 틀림이 됩니다. 각을 지나며 한꺼번에 바뀐 것은 이 때문이라고 봤습니다.

다만 이 진단은 에이전트와 함께 코드 구조로 추론한 것입니다. 그때의 음높이 로그를 다시 넣어 재현하지는 않았습니다.

고친 방법: 지나간 음은 고정하고, 추정은 덜 흔들리게

두 가지를 바꿨습니다.

지나간 음의 색을 고정합니다. 연주 위치가 바뀔 때마다, 지금 음보다 두 음 앞까지의 색을 그 시점 값으로 고정합니다. 고정한 음은 뒤에서 조율 추정이 바뀌어도 다시 칠하지 않고, 늦게 도착한 값도 넣지 않습니다.

fun freezeBefore(song: Song, index: Int): LivePitchTally {
    val passed = song.timeline.take(index.coerceAtLeast(0)).map { it.id }.filter { it in notes && it !in frozen }
    if (passed.isEmpty()) return this
    val live = marks(song)
    return copy(frozen = frozen + passed.mapNotNull { id -> live[id]?.let { id to it } })
}

화면 쪽에서는 freezeBefore(song, position - 1)로 부릅니다. 바로 앞 음까지 고정하지 않는 이유가 있습니다. 직전 음의 판정 결과는 다음 음으로 넘어간 뒤에도 늦게 도착할 수 있습니다. 그래서 한 음을 더 열어 둡니다.

조율 추정을 덜 흔들리게 합니다. 서버는 모든 프레임의 중앙값으로 조율 차이를 냅니다. 실시간에서는 음마다 값 하나(가운데 60% 중앙값)만 추정에 넣었습니다. 그리고 ±150센트 밖으로 벗어난 음은 추정에서 뺐습니다. 다른 음을 불었거나 박자가 어긋나 앞뒤 소리가 섞인 값으로 보는 것입니다. 이렇게 하면 긴 음 하나가 추정을 끌고 가거나, 섞인 소리 하나가 상한을 넘겨 보정을 꺼 버리는 일이 줄어듭니다.

±50센트 판정과 보정 상한은 서버와 같게 두었습니다. 실시간에서만 다른 부분은 이 두 가지입니다.

진행 바가 지나간 뒤에만 색을 보여 주기

이후 다른 문제가 하나 더 나왔습니다. 판정 색이 지금 연주 중인 칸 위에 바로 칠해지면서, 그 칸에 차오르던 회색 진행 표시를 가렸습니다. 연주자가 지금 어디를 불고 있는지 보기 어려웠습니다.

그래서 진행 위치가 칸의 끝을 다 지난 뒤에만 판정 색을 보이게 했습니다.

internal fun unitPassed(unit: ScoreDisplayUnit, position: Double?): Boolean =
    position != null && position >= unit.unitStart + unit.unitDuration - PassedEpsilon

한 정간이 여러 소박으로 나뉜 곳은 진행이 지나간 소박부터 하나씩 칠해집니다. 연주가 끝나 진행 표시가 사라지면 모아 둔 색이 모두 보입니다. 이 옵션은 평가 화면에서만 켜고, 다른 화면의 칸 표시는 그대로 두었습니다.

색 고정과 같은 생각입니다. 아직 끝나지 않은 음의 판정은 화면에 내놓지 않습니다.

확인한 결과와 한계

확인기기결과
지나간 음 색 고정Galaxy S10(Android 12), 디버그 빌드각을 지나도 앞 음 색이 유지됨
진행 뒤 색 표시Galaxy S25(Android 16), 디버그 빌드연주 중인 칸에는 회색 진행만, 지나간 칸에 판정 색

두 확인 모두 제가 직접 연주하며 본 결과입니다. 자동 테스트로는 조율 추정 함수와 색 고정, 칸 통과 판정을 따로 검사합니다.

확인하지 못한 것도 분명히 남겨 둡니다.

  • 실시간 칸 색이 결과 화면의 음정 틀림과 얼마나 맞는지는 실기기에서 비교하지 않았습니다.
  • 색 고정 때문에 생기는 차이도 있습니다. 고정된 색은 그 시점의 추정으로 판정한 값이라, 녹음 전체로 판정하는 서버 결과와 다를 수 있습니다.
  • 멈춤·처음부터 다시·화면 이탈 때 색이 지워지는지는 자동 검사로만 확인했습니다.
  • Android 태블릿과 iOS에서는 보지 않았습니다. iOS는 아직 녹음 중 음높이 측정이 없습니다.

남은 과제

  • 결과 화면과의 비교. 같은 연주에서 실시간 색과 결과 화면의 음정 틀림을 나란히 놓고 얼마나 다른지 재 보려고 합니다. 결과 화면에서는 박자·미검출 표시를 빼고 음정만 봐야 공정한 비교가 됩니다.
  • 원인 재현. 보정 상한에서 판정이 뒤집힌다는 진단을 실제 로그로 재현해 보지 않았습니다. 기기 로그를 판정 코드에 다시 넣어 보면 확인할 수 있습니다.
  • 기준 공유. 실시간 색에 서버 음정 기준을 쓰기로 한 결정은 채점 기준을 맡은 팀원의 확인이 필요합니다.

서버 규칙은 녹음 전체를 다 본 뒤 한 번 판정한다는 전제 위에 서 있습니다. 같은 규칙을 실시간으로 옮기면 중간값이 계속 바뀐다는 새 문제가 생깁니다. 이번에는 이미 보여 준 것을 다시 바꾸지 않는 쪽을 택했습니다.
