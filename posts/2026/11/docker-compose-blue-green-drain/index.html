얼쑤는 Docker Compose에서 백엔드를 어떻게 무중단으로 교체할까

얼쑤의 Compose·Nginx 블루그린 구조와 트래픽 전환, 악보 변환 작업 보호, DB 호환성 검증을 설명합니다.

우동균·2026.11.09
이 글의 목차
  • 같은 호스트에 백엔드 슬롯 두 개를 뒀다
  • 준비, 전환, 종료를 각각 확인한다
  • HTTP 응답 뒤에도 작업이 계속된다
  • 무엇으로 동작을 확인했나

백엔드 컨테이너 하나를 새 버전으로 교체하면, 이전 컨테이너가 내려간 시점과 새 컨테이너가 요청을 받을 수 있는 시점 사이에 공백이 생긴다. 이 공백을 없애려면 순서를 바꿔야 한다. 이전 버전이 요청을 받는 동안 새 버전을 준비하고, 연결을 넘긴 뒤에도 이미 받은 요청과 작업을 마칠 때까지 이전 버전을 살려 둔다. 얼쑤는 기존 Docker Compose와 Nginx에 이 순서를 적용했다.

같은 호스트에 백엔드 슬롯 두 개를 뒀다

슬롯은 백엔드 한 인스턴스를 실행하는 자리다. Compose에 블루와 그린을 정의하고, 두 슬롯이 같은 런타임 설정을 쓰도록 했다. 배포할 때 비활성 슬롯에 새 버전의 JAR을 붙인다. 두 슬롯은 같은 MySQL을 사용한다. 사용자는 평소와 같은 HTTPS 주소로 접속하고, Nginx가 활성 슬롯으로 요청을 보낸다.

사용자 ── HTTPS ──> Nginx
                     ├──> 블루 백엔드  ──┐
                     └──> 그린 백엔드  ──┴──> 공유 MySQL

평상시에는 한 슬롯만 실행한다. 블루가 활성이라면 다음 배포는 그린에서 준비한다. 그린이 활성화되면 그다음 배포는 블루에서 준비한다. 기존 Compose에 슬롯을 추가한 이유는 정기 배포에서 교체할 대상이 백엔드 한 서비스였기 때문이다. 두 JVM이 겹치는 구간에는 CPU·메모리와 DB 연결 여유가 필요하다.

준비, 전환, 종료를 각각 확인한다

Jenkins는 develop의 변경을 감지해 체크아웃한 커밋을 빌드한다. 같은 커밋의 산출물을 배포 스크립트에 넘기면, 스크립트가 활성 슬롯을 읽고 반대쪽에서 새 버전을 준비한다.

단계확인하는 것실패하거나 작업이 남았을 때
준비대기 슬롯의 준비 상태와 운영 DB 연결 대상기존 슬롯으로 계속 응답
전환Nginx 설정 검사와 리로드, 실제로 로드된 슬롯, HTTPS 준비 상태와 API 응답살아 있는 이전 슬롯으로 경로 복구
종료이전 워커 종료, 진행 중인 업무 처리 완료, 새 슬롯 준비 상태이전 슬롯을 유지하고 다시 확인

Nginx 리로드가 성공하면 새 워커가 새 연결을 받고, 이전 워커는 이미 맡은 연결을 처리한 뒤 종료한다. 이전 워커가 블루에 요청을 전달할 수 있으므로, 그린에서 정상 응답을 받았어도 블루를 내리기 전에 이전 워커의 종료를 확인한다. 배포 스크립트는 전환 전 상태를 기록한다. 실행이 중단되면 다음 실행이 그 기록을 읽어 복구부터 시작한다. Nginx 설정 리로드 문서

HTTP 응답 뒤에도 작업이 계속된다

얼쑤에서 악보를 올리면 HTTP 요청이 끝난 뒤에도 인식 작업이 큐에 남는다. 작업 상태는 공유 DB에 있지만, 임시 원본과 읽기 권한은 접수한 슬롯에 연결돼 있다. 그린이 블루의 작업을 가져가면 같은 DB 행을 읽어도 원본을 처리할 수 없다.

그래서 임시 원본 키에 접수 슬롯을 표시했다. 각 슬롯은 자기 작업만 가져오고, 시작할 때도 자기 슬롯의 미완료 작업만 복구한다. 인식 서비스가 원본을 읽을 때도 접수한 슬롯으로 연결한다. 이전 슬롯을 내리기 전에는 Nginx 워커뿐 아니라 그 슬롯의 대기·진행 중인 악보 변환과 실행 중인 음원 작업도 확인한다. 정해진 대기 시간 안에 끝나지 않으면 종료를 미룬다.

공유 DB의 스키마도 배포 순서에 영향을 준다. 얼쑤는 필요한 Flyway 변경을 전환 전에 적용하므로, 변경된 스키마를 기존 버전과 새 버전이 함께 사용할 수 있어야 한다. 트래픽을 이전 슬롯으로 돌리는 절차와 DB 스키마 복구 절차는 각각 관리한다.

무엇으로 동작을 확인했나

격리된 Docker 환경에서 실제 Nginx와 시험용 백엔드 두 개를 띄웠다. 블루에서 그린으로 전환하고 다시 블루로 돌아오는 동안 연속 HTTPS 요청 104건이 모두 응답했다. 전환 직전에 블루가 받은 업로드는 그린이 응답하기 시작한 뒤에도 블루에서 마무리됐고, 응답에 담긴 SHA-256은 보낸 본문과 일치했다.

별도의 임시 MySQL 테스트에서는 그린이 시작해도 블루의 진행 중인 변환이 보존되고, 각 슬롯이 자기 작업만 가져가는 것을 확인했다. 후속 운영 배포에서는 Jenkins가 의도한 병합 커밋을 포함하는 버전을 체크아웃했고, 자동 배포 단계까지 성공했다. 요청 104건은 격리 환경의 관찰값이다.

이 구조를 처음 설치할 때는 라우팅 설정을 마운트하기 위해 컨테이너를 재생성하는 작업이 필요했다. 그 이후 정기 배포에서는 새 슬롯의 준비, 새 연결의 전환, 이전 요청과 비동기 작업의 완료를 차례로 확인한 뒤 백엔드를 교체한다.
