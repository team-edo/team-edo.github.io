목록을 열 때 GET을 8건에서 1건으로 줄이기

곡별 요약과 첫 페이지로 연습 기록 목록을 열고, 나머지는 펼칠 때 조회하도록 바꿨습니다. Galaxy S10에서 요청 수와 첫 카드 표시를 각각 확인했습니다.

얼쑤의 연습 기록 화면에서는 곡별로 몇 번 연주했는지와 최고점을 먼저 볼 수 있습니다. 화면을 열면 한 곡이 펼쳐지고, 나머지 곡은 이름과 요약만 보입니다. 이전 앱은 화면을 열 때 접혀 있는 곡의 기록까지 미리 조회했습니다. 운영 서버에 연결한 Galaxy S10에서 이 화면을 한 번 열 때 GET 8건이 나갔습니다.

화면을 처음 구성하는 데 필요한 데이터를 다시 정했습니다. 곡별 요약은 한 번에 받고, 기록 행은 처음 펼쳐진 곡의 첫 페이지만 받습니다. 나머지 기록은 사용자가 곡을 펼치거나 더 보기를 누를 때 요청합니다. 운영 HTTPS 재측정에서 진입당 관측된 GET은 8건에서 1건으로 줄었고, 화면 제목이 보인 뒤 첫 카드가 나타나기까지의 중앙값은 633ms에서 283ms로 줄었습니다.

모든 곡의 요약과 한 곡의 기록 페이지

기존 연습 기록 API에도 곡별 페이지가 있었습니다. 이전 앱은 첫 응답에서 기록이 있는 곡 목록과 기본 곡의 첫 페이지를 받았습니다. 이 첫 페이지를 재사용해 같은 곡의 후속 페이지를 먼저 읽고, 다른 모든 곡도 첫 페이지부터 끝까지 순차적으로 조회했습니다. 곡을 악기로 분류할 때는 악기·곡 카탈로그도 조회했습니다. 실측 계정의 이전 앱에서 관측한 8건은 기록 목록 5건, 악기 목록 1건, 곡 목록 1건, 보충 곡 상세 1건이었습니다. 곡 상세는 매번 404로 끝났으며, 요청이 전송됐으므로 합계에 포함했습니다.

개선 앱은 같은 API로 곡별 요약과 기본 곡의 첫 페이지(최대 20개 기록)을 함께 받습니다. 요청에서 songId를 생략하면 API가 곡 순서의 첫 곡을 고릅니다. 새 화면은 최근 연주 시작 시각 기준의 곡 순서를 명시합니다. 기존 호출에서 사용하는 최근 저장 기준 기본값은 유지했습니다. 서버가 곡별 최신 연주 시각, 기록 수와 최고점을 집계하므로 화면은 아직 펼치지 않은 곡의 머리도 채울 수 있습니다. 주간 요약도 요청한 주의 저장 기록 전체에서 집계합니다.

응답에 담는 정보화면에서 쓰는 곳
모든 곡의 제목·기록 수·최고점·악기 코드접힌 곡의 머리와 악기 필터
선택된 한 곡의 기록 행과 페이지 수펼친 곡의 내용과 더 보기
요청한 주의 기록 수와 최고점주간 요약

악기 코드를 앱에서 알아볼 수 있으면 곡 요약만으로 분류합니다. 코드가 빠졌거나 앱이 모르는 값이면 카탈로그에서 보완하고, 거기에도 정보가 없으면 해당 곡 상세를 확인합니다. 악기를 끝내 확인하지 못한 곡은 전체에서 볼 수 있습니다. 계정에 따라 보충 요청이 발생할 수 있으므로 실측의 1건은 당시 휴대폰 기본 진입에서 관측한 값입니다.

다른 곡을 펼칠 때 드는 비용

다른 곡을 처음 펼치면 그 곡의 0페이지를 읽습니다. 더 보기는 서버가 알려준 페이지 수 안에서 다음 페이지를 이어 붙입니다. 조회에 실패하면 받아 둔 행을 유지하고 같은 페이지를 다시 요청할 수 있습니다. 같은 화면에서 정렬을 유지한 채 곡을 접었다 다시 펼치면 받은 페이지를 재사용합니다. 정렬이 바뀌면 이전 정렬에서 받아 둔 페이지는 비웁니다.

운영 HTTPS 예비 측정에서 두 버전으로 같은 곡을 한 번씩 펼쳤을 때 GET은 0→1건, 앱의 첫 행 그리기는 44→119ms였습니다. 두 버전 모두 재펼치기의 추가 GET은 0건이었습니다. 로컬 고정 데이터 비교에서도 다른 곡을 처음 펼칠 때 0→1건이었습니다. 이 변경은 일부 조회를 진입에서 첫 펼치기로 옮겼습니다. 여러 곡을 열고 더 보기를 반복하는 전체 이용 흐름의 요청 합계는 측정하지 않았습니다.

요청이 줄어든 뒤 실제 화면에서 확인하기

Android 12의 Galaxy S10 한 대에서 동일한 검증 계정으로 운영 HTTPS에 접속했습니다. 이전·개선 디버그 APK를 각각 10회 실행했습니다. 매회 앱 프로세스를 다시 시작하고 홈 요청이 끝나면 USB로 기록 목록 버튼을 눌렀습니다. 각 쌍에서 먼저 실행할 버전을 교대로 바꿨습니다.

지표이전개선변화
목록 진입당 계측된 GET 합계8건1건87.5% 감소
목록 진입당 연습 기록 목록 GET5건1건80% 감소
앱 버튼 처리 → 마지막 GET 본문 수신 완료 중앙값573.5ms133ms76.8% 단축
앱 버튼 처리 → Compose 첫 곡 카드 그리기 중앙값745.5ms381.5ms48.8% 단축
외부 영상의 화면 제목 → 첫 곡 카드 표시 중앙값633ms283ms55.3% 단축

마지막 GET은 진입 중 관측한 요청의 본문 종료 시점이며 이전 앱의 404 응답도 포함합니다. 앱 로그의 첫 카드 이벤트는 Compose가 카드의 그리기 코드를 실행한 뒤 기록합니다. 응답 이후에도 상태 반영과 화면 그리기가 남고, 먼저 그릴 데이터가 준비되면 다른 GET이 끝나기 전에 카드가 보일 수도 있습니다.

외부 영상은 다른 구간을 잽니다. 30fps 원본에서 실제 첫 곡 카드 이름이 처음 읽힌 프레임의 표시 타임스탬프(PTS)에서 연습 기록 제목이 처음 읽힌 프레임의 PTS를 뺐습니다. 두 지표는 시작점도 끝점도 다르므로 둘의 차이를 기기의 화면 출력 지연으로 해석할 수 없습니다. 영상으로 확인한 카드 표시 범위는 이전 533–1,100ms, 개선 267–300ms였고, 10쌍 모두 개선 버전이 빨랐습니다.

한 프레임 사이에 일어난 일의 정확한 시각은 영상만으로 알기 어렵습니다. 그래서 제목과 카드 각각에 대해 직전 프레임과 최초 식별 프레임을 사용했습니다. 가능한 지연의 하한은 카드 직전 PTS − 제목 최초 PTS와 0 중 큰 값, 상한은 카드 최초 PTS − 제목 직전 PTS입니다. 이전 지연의 하한과 개선 지연의 상한을 비교해도 각 쌍에서 최소 200ms 차이가 났습니다. 시간 수치는 한 기기·한 계정에서 두 빌드를 비교한 값입니다. 개별 변경이 단축에 기여한 크기와 터치 순간부터 패널 표시까지의 시간은 따로 측정하지 않았습니다.

같은 원리를 내 악보 목록에 적용하기

악보 편집기에서도 비슷한 조회가 있었습니다. 사용자가 악기를 고르면 앱은 목록의 각 악보를 어느 악기로 분류할지 확인하려고 상세를 읽었습니다. 목록 API에 instrumentCode를 제공한 뒤에는 최신 목록의 코드가 비어 있지 않은 항목을 그 자리에서 분류할 수 있었습니다. 서버는 확정본이 있으면 먼저 편집기가 읽을 수 있는 형식인지 검사합니다. 초안이 있으면 초안의 기준 판본이 현재 악보 판본과 일치하고 문서 검증을 통과할 때 초안의 악기 코드를 사용합니다. 초안이 없으면 확정본에서 악기 코드를 읽습니다. 확정본이나 초안의 검증에 실패하거나 사용할 악기 코드가 없으면 instrumentCode는 null입니다.

목록이 최신이고 코드가 비어 있으면 상세에서 악기를 확인합니다. 구버전 응답에 필드가 빠졌을 때도 같은 경로를 씁니다. 상세 조회 결과를 수정 시각으로 재사용할 수 있는 경우는 최신 목록에서 초안이 없는 행으로 제한했습니다. 자동 저장은 목록 수정 시각을 바꾸지 않기 때문입니다. 목록 갱신 자체가 실패하면 직전 목록에 남은 행의 이전 코드와 상세 캐시를 건너뛰고 상세를 다시 읽습니다. 상세를 읽지 못한 행은 필터 결과에서 제외하고 확인하지 못한 건수에 포함합니다. 갱신 실패와 손상된 초안은 호스트 회귀 테스트로 확인했습니다.

Galaxy S10에서 USB로 연결한 로컬 HTTP 서버에 동일한 악보 4행을 두고, 두 APK의 순서를 바꿔 버전별 12회씩 비교했습니다. 세 번의 예열은 각 버전 집계에서 제외했습니다.

사용자 동작변경 전 → 후
첫 단소 선택에서 악보 상세 GET4→2건(50% 감소)
앱의 첫 단소 선택 처리 → 목록 탭 첫 그리기 중앙값467.11→368.75ms(21.1% 단축)
앱의 소금 전환 처리 → 소금 행 첫 그리기 중앙값176.01→182.32ms(3.6% 증가)

소금 전환에는 두 버전 모두 악보 상세 GET이 0건이었습니다. 블록별 시간 차이의 방향은 섞였고, 개선 앱에서 한 번 관측된 2.23초 지연의 원인은 확인하지 못했습니다. 이 실험의 시간은 로컬 HTTP 환경에서 기록한 Compose 그리기 지표입니다.

다른 목록을 바꿀 때 먼저 볼 것

첫 화면의 각 요소가 어떤 데이터에 의존하는지 적어 보면, 모든 행에 공통인 요약과 사용자가 열 때 필요한 상세를 나눌 수 있습니다. 상세를 미뤘다면 진입과 첫 펼치기, 재펼치기의 요청 수를 각각 세어 비용이 어디로 갔는지 확인할 수 있습니다. 목록 필드로 상세 조회를 생략할 때는 그 필드를 믿을 수 있는 조건과 갱신 실패 시 동작까지 계약에 포함해야 합니다.

다음에는 몇 곡을 펼치고 더 보기를 얼마나 쓰는지에 따라 한 번의 목록 이용에서 드는 총 요청 수를 비교해 볼 수 있습니다.
