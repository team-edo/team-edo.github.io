Spring 테스트 53개 실패와 MySQL 연결 한도

얼쑤의 MySQL 통합 테스트 174개 중 53개가 실패한 기록을 바탕으로, Spring이 캐시한 컨텍스트의 연결 풀이 어떻게 DB 한도에 닿는지 살펴봅니다.

우동균·2026.11.08

  • 연결 한도를 바꿔 재검증
  • 연결이 실제로 쌓였는지 확인하는 법

얼쑤 백엔드의 databaseTest는 Spring 애플리케이션과 실제 MySQL을 연결해 실행하는 통합 테스트입니다. 앞선 실행에서 161개가 모두 통과했는데, 다른 변경을 병합한 뒤에는 174개 중 53개가 실패했습니다. 서로 다른 기능을 확인하는 테스트에서 같은 메시지가 45번 나왔습니다. Too many connections였습니다.

테스트보다 먼저 연결 확인

Spring 테스트가 애플리케이션 컨텍스트를 올리는 도중 DB에 연결하지 못하면 테스트 코드까지 실행되지 못합니다. 같은 설정의 컨텍스트를 여는 데 이미 실패한 뒤에는 Spring이 다음 로딩 시도를 건너뛰면서 ApplicationContext failure threshold exceeded를 남길 수 있습니다. 이 메시지만 보면 원인이 비슷한 실패가 여러 개 생긴 것처럼 보입니다. 앞선 로딩 실패의 예외까지 내려가면 MySQL이 새 연결을 거부했다는 단서가 나옵니다. Spring의 컨텍스트 로딩 실패 정책 · MySQL의 연결 초과 오류

테스트 뒤에 남는 연결 풀

Spring은 같은 설정의 테스트가 애플리케이션을 반복해서 띄우는 비용을 줄이려고 컨텍스트를 캐시합니다. 활성 프로필이나 테스트 속성, 대체한 빈이 다르면 다른 캐시 키가 생길 수 있습니다. 이때 같은 MySQL을 쓰는 여러 컨텍스트가 각자의 HikariCP 연결 풀을 띄우면, 먼저 끝난 테스트의 컨텍스트도 캐시에 남아 DB 연결을 유지할 수 있습니다. 테스트를 순서대로 실행해도 나중에 시작한 컨텍스트의 연결과 앞서 열어 둔 연결이 겹치는 이유입니다. Spring의 컨텍스트 캐시

HikariCP의 maximumPoolSize는 풀 하나가 열 수 있는 연결의 상한이고, minimumIdle은 풀이 유지하려는 유휴 연결 수입니다. MySQL의 max_connections는 같은 인스턴스에 붙는 클라이언트 전체에 적용됩니다. 풀 하나의 설정만 보면 여유가 있어도, 여러 풀이 사용하는 연결을 합하면 새 컨텍스트를 올릴 자리가 부족해질 수 있습니다. HikariCP의 연결 풀 설정

연결 한도를 바꿔 재검증

max_connections는 인스턴스 전체에 적용됩니다. 한도를 바꿀 실험은 테스트가 끝나면 폐기할 별도 MySQL에서 진행했습니다. 당시에는 컨텍스트별 연결 수나 전체 최대 동시 연결 수를 기록하지 않았습니다.

통합 테스트의 데이터도 실행 단위로 분리했습니다. 테스트를 실행할 때 임시 DB와 전용 사용자를 만들고, 그 사용자의 권한은 해당 DB로 한정했습니다. 테스트가 실패해도 정리 단계에서 실행용 DB와 사용자를 제거하는 절차를 둡니다. 스키마를 나누는 것만으로는 같은 인스턴스의 연결 한도가 나뉘지 않습니다. 이 실험에서 별도의 MySQL을 쓴 이유는 연결 한도도 운영 DB와 분리해 바꿀 수 있기 때문입니다.

폐기용 MySQL 8.4의 연결 한도를 기본값 151에서 1,000으로 올린 뒤, 병합 후의 같은 테스트 묶음을 다시 실행했습니다. 바꾼 조건은 테스트 인스턴스의 연결 한도였습니다. 처음에 53개가 실패했던 174개가 두 번째 실행에서는 모두 통과했습니다. MySQL의 max_connections 설정

연결이 실제로 쌓였는지 확인하는 법

Spring의 테스트 로그에서 org.springframework.test.context.cache를 DEBUG로 켜면 캐시가 보관한 컨텍스트 수를 볼 수 있습니다. 이 수는 열린 DB 연결 수와는 별개입니다. 연결 풀이 시작됐다는 로그는 풀 개수를, MySQL의 Max_used_connections는 그 인스턴스가 동시에 받아들인 연결의 최고치를 보여 줍니다. Connection_errors_max_connections가 실행 중 늘었다면 MySQL이 한도에 닿아 새 연결을 거부한 것입니다. 같은 실행에서 이 값들을 나란히 기록하면 어디서 더 많은 연결이 만들어졌는지 좁힐 수 있습니다.

당시 테스트 코드를 별도의 MySQL 8.4.9에서 다시 실행했습니다. 이 환경에서는 두 조건 모두 테스트 171개가 집계됐습니다. 같은 테스트 명령과 권한을 쓰고, 매번 빈 스키마를 준비한 뒤 인스턴스의 연결 한도만 바꿨습니다.

시작이 완료된 HikariCP 연결 풀17개32개
MySQL이 기록한 동시 연결 최고치152개302개

151에서 먼저 연결이 거부됐고, 이어 컨텍스트를 열지 못한 여러 테스트가 실패했습니다. 1,000에서는 더 많은 컨텍스트와 풀이 시작됐고 같은 테스트 묶음이 모두 통과했습니다. 이 표는 당시의 174개 실행과 별도로, 캐시와 서버 지표를 함께 기록한 로컬 재현입니다. MySQL의 최고치는 인스턴스 전체 수치라 풀 하나가 연결을 몇 개씩 유지했는지는 알려 주지 않습니다.

폐기용 MySQL이 시작 직후 종료됐으면 연결 수를 세기 전에 시작 로그부터 확인합니다. 폐기용 MySQL을 실행 단위로 분리한 이유에 서버가 시작하기도 전에 소켓 경로 길이로 실패한 별도 사례를 정리했습니다.
