시김새의 그림과 소리를 한 데이터로

시김새를 음높이 곡선 하나로 저장해 붓질 그림과 예시 소리를 함께 만들고, 단소 녹음을 재서 소리를 합성하고, 붓질과 소리를 같은 시계에 묶은 과정입니다.

얼쑤의 ‘정간보 쉽게 읽기’에는 시김새 쪽이 있습니다. 시김새 이름을 누르면 창이 열리고, 그 시김새를 부는 모양이 붓으로 먹을 긋듯 그려집니다. 선이 그어지는 동안 그 모양대로 부는 단소 소리가 함께 납니다.

이 창을 만들면서 정한 원칙은 하나였습니다. 그림과 소리를 같은 데이터에서 만든다는 것입니다. 구현은 AI 코딩 에이전트에게 맡겼고, 저는 시안을 보고 소리를 직접 들으며 방향을 정했습니다.

시김새는 음을 꾸미는 방법

국악에서는 적힌 음을 늘 같은 높이로 길게 불지 않습니다. 끝을 밀어 올리기도 하고(추성), 아래 음으로 꺾어 내리기도 하고(퇴성), 흔들기도 합니다(요성). 본음 앞에서 위 음을 짧게 스치기도 합니다(니레·니라·니로). 이렇게 음을 꾸미는 방법을 시김새라고 하고, 정간보에는 율명 옆에 기호로 적습니다.

기호만 보고는 어떻게 부는지 알기 어렵습니다. 저장소에 정리한 입문 지도 자료 조사에서도 공식 자료들은 시김새를 입문 과정의 마지막 단계에 둡니다. 처음에는 모범 연주를 듣고 따라 하라고 합니다. 그래서 ‘처음 배우는 시김새’ 11개는 창을 열면 그림과 소리로 보여 주고, 나머지 ‘더 많은 시김새’ 35개 기호는 누르면 한 줄 설명만 나오게 했습니다.

곡선 하나로 그림과 소리를

부는 모양은 가로가 시간, 세로가 음높이인 곡선으로 저장합니다. SVG path 문자열을 그대로 씁니다.

/**
 * viewBox 72×38, 적힌 음 높이 y=24, 한 음 = 6. [curve]는 부는 소리 선(SVG path),
 * [tail]은 가늘어지며 흐려지는 꼬리(채운 도형), [end]는 적힌 길이의 끝(눈금을 긋고 적힌 음 점선도 여기까지).
 */
data class Curve(
    val curve: String,
    val tail: String? = null,
    val end: Float? = null,
    override val unit: Float = 6f,
    val vibrato: Boolean = false,
) : SigimsaeFigure
시김새곡선뜻
추성M4 24H44C54 24 60 22 68 12적힌 음으로 불다가 끝에서 위로 휘어 오른다
퇴성M4 24H46L51 32H68, unit = 8끝에서 아래로 꺾여 내려간다
요성·농음물결 path, vibrato = true적힌 음 둘레를 오르내린다
니레Grace([1])한 음 위에서 본음으로 미끄러져 내려온다

앞에서 스치는 시김새는 곡선을 직접 적지 않고 Grace(steps)에 ‘본음에서 몇 음 위인지’만 적습니다. gracePath가 그 값으로 path를 만듭니다. 같은 함수가 소리를 만드는 스크립트에도 있습니다.

그림 데이터에 소리만을 위한 값이 두 개 있습니다. vibrato와 unit입니다. 퇴성 그림은 한 음 간격(6)보다 크게 8만큼 꺾어 둬야 또렷하게 보였습니다. 그대로 소리로 바꾸면 한 음보다 더 내려가므로, unit = 8로 두어 소리는 정확히 한 음 아래에 닿게 했습니다.

소리는 앱에서 합성하지 않습니다. 웹 시안에서 Web Audio로 만들던 합성을 Node 스크립트로 브라우저 없이 다시 계산해 MP3 11개를 미리 만들어 둡니다. 스크립트는 곡선의 세로 위치를 ‘적힌 음에서 몇 음’으로 바꾸고, 평조 음계를 따라 주파수로 옮깁니다. 적힌 음은 단소로 부는 황(약 622Hz)으로 둡니다.

const HWANG = 622.25;                     // 단소로 부는 황(黃) ≈ E♭5
const PYEONG = [-5, -3, 0, 2, 5, 7, 9];   // 평조: 황에서 반음 수
function sigFreq(step) {
  const k = step + 2, i = Math.max(0, Math.min(PYEONG.length - 2, Math.floor(k)));
  return HWANG * 2 ** ((PYEONG[i] + (PYEONG[i + 1] - PYEONG[i]) * (k - i)) / 12);
}

처음에는 곡선 높이를 그대로 따라가서 음과 음 사이를 느리게 미끄러졌습니다. 미끄러짐을 덜 느리게 해 달라고 하자, 음과 음 사이는 빨리 지나가고 음 자리에서는 머물도록 settle이라는 보정이 들어갔습니다. 요성과 흘림표 꼬리에는 이 보정을 걸지 않았습니다. 떨림과 흘러내림 자체가 그 시김새의 모양이기 때문입니다.

“노래 같다"에서 “너무 바람"까지

소리 모양은 처음부터 맞지 않았습니다. 시안에서 들어 보고 고치기를 여러 번 했습니다.

차례제 의견바꾼 것
1숨소리를 줄이고, 음 사이 미끄러짐을 덜 느리게숨소리를 약 1/3로 줄이고, 음 사이를 빠르게 지나가게 함
2악기보다 사람이 부르는 노래에 가깝다. 더 중후한 바람 소리였으면규칙적인 떨림(비브라토)을 빼고 바람 소리를 중심에 둠. 소리 전체를 한 옥타브 낮춤
3이번에는 너무 바람 소리다. 대금으로 부는 황을 기준으로기준음을 대금의 황으로 되돌리고, 배음이 차례로 약해지는 관 소리로 바꿈
4단소 녹음을 건네며 이걸 참고해 달라녹음을 재서 그 값으로 합성

2번에서 세션은 노래처럼 들리는 원인을 맑은 단음과 규칙적인 떨림으로 판단했습니다. 떨림을 뺀 것은 맞았지만, “중후하게"를 옥타브를 내리는 것으로 옮기자 악기다운 소리가 흐려졌고 다음 의견은 “너무 바람 소리"였습니다. 형용사로 소리를 맞추는 일은 한쪽으로 고치면 반대쪽으로 넘어갔습니다. 그래서 4번에서는 말 대신 실제 녹음을 기준으로 삼았습니다.

녹음을 재서 합성하기

녹음 146초에서 0.35초 넘게 같은 높이로 분 음을 찾고, 그중 단소 황 둘레의 음을 골라 쟀습니다.

항목녹음에서 잰 값
배음바탕음이 대부분. 3배음 −14dB, 2배음 −29dB로 홀수 배음이 더 셈
숨(배음 사이 잡음)전체 소리보다 약 −28dB
음높이 흔들림5~7센트. 초당 3번 남짓, 고르지 않게 흔들림
세기 흔들림3~9%
소리가 들어가는 시간약 0.04초

이 값을 거의 그대로 합성에 넣었습니다. 배음 세기는 파형 표의 계수로, 숨은 네 개 대역으로 나눈 잡음으로 섞었습니다. 숨은 첫소리에서만 세게 들어가게 했습니다. 음높이와 세기의 흔들림은 일정한 주기의 떨림(LFO)이 아니라, 저역 통과 필터를 거친 잡음으로 만들었습니다.

const DANSO_HARM = [0, 1, .036, .201, .021, .037, .010, .012, .004, .004, .002];
const detune = drift(4, 5), wobble = drift(6, .05);   // 음높이 ±5센트 남짓, 세기 ±5% 남짓

.201이 약 −14dB인 3배음, .036이 약 −29dB인 2배음입니다. 3번에서 넣었던 대금의 청 울림은 뺐습니다. 단소에는 청이 없기 때문입니다.

맞게 됐는지는 합성한 소리를 파일로 만들어 녹음과 같은 방법으로 다시 재서 비교했습니다.

항목녹음합성
배음(2·3·4·5배)−28.8 / −14.0 / −33.6 / −28.6dB−28.9 / −14.2 / −33.9 / −29.0dB
숨(대역 네 곳)−36.5 / −32.4 / −34.9 / −35.5dB약 −36.4 / −33.4 / −33.2 / −33.9dB

배음은 1dB 안에서 같았습니다. 숨은 처음 높은 대역이 3dB쯤 커서 줄였고, 2dB 안으로 맞췄습니다. 녹음 한 개에서 고른 음들을 한 번 잰 비교입니다. 녹음 파일은 시안과 앱에 넣지 않았고 잰 숫자만 썼습니다.

상시 떨림을 뺐어도 요성은 그대로 떨립니다. 요성의 떨림은 음색에 늘 얹는 떨림이 아니라 그림 곡선을 따라가는 음높이 변화로 만들기 때문입니다. 이 단계의 소리를 듣고 단소 소리로 두기로 정했습니다.

붓질과 소리를 한 시계에

웹 시안에서 붓질은 SVG SMIL 애니메이션이었습니다. 끝이 흐린 가리개를 왼쪽에서 오른쪽으로 밀어 선을 드러내고, keySplines .5 0 .35 1로 처음엔 천천히 대다가 뒤로 갈수록 흘러가게 했습니다. 한 바퀴 3.6초 중 2.16초 동안 긋습니다. 나중에 되풀이하지 않고 한 번만 긋도록 바꿨습니다.

시안에서 먼저 걸린 것은 창을 열면 붓질이 중간부터 보이는 문제였습니다. SMIL <animate>는 요소가 보이는 순간이 아니라 그 <svg>의 타임라인을 따라 진행합니다. 페이지가 열린 뒤로 시간이 계속 흘러서, 늦게 연 창은 이미 진행된 지점부터 보였습니다. 창을 열 때 svg.setCurrentTime(0)으로 시계를 되돌려 해결했습니다. 브라우저마다 다른지는 확인하지 않았습니다.

소리가 붓끝 높이를 따라가려면 소리 쪽도 붓질과 같은 시간표를 써야 합니다. 스크립트는 keySplines의 곡선을 cubic-bezier로 거꾸로 풀어 시각마다 붓끝의 x를 구하고, 그 x에서 곡선의 높이를 읽어 주파수를 정합니다. Compose 앱으로 옮길 때 같은 계수의 CubicBezierEasing을 썼습니다. 그래서 두 언어의 붓끝 위치가 같은 식이 됩니다.

private val BrushEasing = CubicBezierEasing(0.5f, 0f, 0.35f, 1f)
internal fun brushMaskX(seconds: Float): Float = -80f + 80f * BrushEasing.transform((seconds / SigimsaeDrawSeconds).coerceIn(0f, 1f))
internal fun brushHead(seconds: Float): Float = if (seconds >= SigimsaeDrawSeconds) 999f else brushMaskX(seconds) + 75f

const sigHead = (t) => t >= SIG_DRAW ? 999 : -5 + 80 * cubicY(Math.max(0, t) / SIG_DRAW, .5, 0, .35, 1);

Kotlin의 brushHead를 풀면 -5 + 80 × ease(t / 2.16)이고, 스크립트의 sigHead와 같습니다. 시간도 하나만 둡니다. 앱은 프레임 시각(withFrameNanos)으로 잰 초 하나로 가리개와 줄 떨림을 함께 움직입니다.

남은 것은 시작점입니다. 미리 만든 음원은 틀자마자 나지 않습니다. 앱의 웹 빌드에서 한 번 재 보니 처음 열 때는 0.45초 뒤, ‘다시 듣기’에서는 50ms 뒤에 소리가 나기 시작했습니다. 붓질을 먼저 시작하면 선이 소리보다 앞서갑니다. 그래서 소리가 나기 시작한 뒤에 붓질 시계를 0초에서 시작합니다.

LaunchedEffect(replay) {
    seconds = 0f
    onStart()
    val start = withFrameNanos { it }
    while (seconds < SigimsaeDrawSeconds) {
        seconds = (withFrameNanos { it } - start) / 1_000_000_000f
    }
    seconds = SigimsaeDrawSeconds
}

onStart는 소리 재생기의 play입니다. 이 함수는 소리가 나기 시작하면 돌아오고, 틀지 못하면 false를 돌려줍니다. 소리를 틀지 못해도 붓질은 그립니다. 시안은 소리를 0.03초 늦게 시작했지만 음원은 0초에 시작하게 만들어, 파일의 처음이 곧 붓질의 처음이 되게 했습니다. ‘다시 듣기’는 replay 값을 올려 이 효과를 처음부터 다시 실행합니다.

시안의 먹 번짐에는 SVG 필터 feDisplacementMap을 썼는데 Compose에는 같은 필터가 없습니다. 고정된 잡음으로 선의 점을 조금씩 옮겨 비슷한 결을 냈습니다.

한계와 남은 과제

  • 소리는 수치로만 검증했습니다. 세션은 소리를 직접 들을 수 없어서 배음과 잡음 세기를 숫자로 비교했고, 귀로 들은 확인은 제가 했습니다. 다른 사람이 들었을 때도 단소처럼 들리는지는 따로 확인하지 않았습니다.
  • 곡선은 교육용 구분입니다. 시김새마다 모양을 구별해 보여 주려고 만든 그림이지, 정간보 기호를 그대로 옮기거나 실제 연주를 측정한 곡선이 아닙니다.
  • 악기별 소리가 없습니다. 음원은 시김새마다 하나라서 대금·소금을 고른 사용자도 같은 단소 소리를 듣습니다.
  • 그림 값이 두 곳에 있습니다. 곡선은 Kotlin 데이터와 소리 스크립트에 따로 적혀 있습니다. 둘이 같은지 검사하는 테스트는 없어서, 그림을 고치면 스크립트도 고치고 음원을 다시 만들어야 합니다.

그림과 소리를 따로 만들었다면 한쪽을 고칠 때마다 둘이 어긋났을 것입니다. 곡선 하나를 기준으로 두니 소리를 고칠 때도 그림을 고칠 때도 같은 값을 보면 됐습니다.
