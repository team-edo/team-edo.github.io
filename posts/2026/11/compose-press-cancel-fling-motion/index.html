눌리고, 끊기고, 튕기는 움직임 다듬기

소리 나는 버튼에만 쓰는 눌림 효과, 중간에 끊겨도 끝 상태가 맞는 축하 애니메이션, 짧게 튕겨도 과정이 보이는 홈 화면 펼침까지 Compose 움직임 세 가지를 다듬은 기록입니다.

움직임은 잘 되면 눈에 띄지 않고, 어긋나면 바로 거슬립니다. 이번에는 얼쑤 앱의 움직임 세 가지를 다듬었습니다. 버튼을 누를 때, 애니메이션이 끊길 때, 화면을 튕길 때입니다. 구현은 AI 코딩 에이전트와 함께 했고, 저는 시안을 비교해 적용 범위와 동작을 정했습니다.

1. 눌림: 소리 나는 버튼에만 출렁임을

신호로 쓰려면 좁게 써야 한다

재생 버튼에 elastic squash 효과를 넣었습니다. 누르는 동안 세로로 10% 납작해지고 가로로 조금 넓어졌다가, 떼면 스프링으로 살짝 튕기며 돌아옵니다.

시안을 비교하며 범위를 정했습니다. 처음 후보는 “▶ 모양 버튼 모두"였습니다. 그런데 ▶ 모양이어도 ‘시작하기’처럼 화면만 넘어가는 버튼이 있습니다. 여기까지 출렁이면 효과가 무엇을 뜻하는지 흐려집니다. 그래서 누르면 바로 소리가 나는 버튼에만 쓰기로 했습니다. 대부분의 화면에서 출렁이는 버튼이 하나 정도라 과하지 않고, “누르면 소리가 난다"는 신호로 읽힙니다.

뺀 버튼도 이유가 있습니다.

  • 5초 이동은 연달아 누르는 버튼이라 출렁임이 겹쳐 묶음 전체가 떨려 보입니다.
  • 녹음 시작은 바로 연주를 준비해야 하는 순간이고, 중단·삭제는 무거운 행동이라 튕기는 느낌이 맞지 않습니다.

운지법의 기본음·요성처럼 한 화면에 많고 빠르게 차례로 누르는 소리 버튼은 빼지 않고, 기본의 60%로 약하게 출렁이게 했습니다.

레이아웃은 그대로, 그릴 때만

효과는 Modifier 하나로 붙입니다. 버튼과 같은 InteractionSource를 받아 누름·뗌을 구독하고, graphicsLayer에서 크기만 바꿉니다.

interactionSource.interactions.collect { interaction ->
    when (interaction) {
        is PressInteraction.Press -> {
            release?.cancel()
            pressedAt = TimeSource.Monotonic.markNow()
            /* 납작하게: 감쇠 0.6, 강성 1500 */
        }
        is PressInteraction.Release, is PressInteraction.Cancel -> {
            release = launch {
                delay(MinPressed - pressedAt.elapsedNow()) // 최소 70ms는 눌린 모양 유지
                /* 튕기며 복귀: 감쇠 0.4, 강성 400 */
            }
        }
    }
}
// ...
graphicsLayer { scaleX = sx.value; scaleY = sy.value }

복귀는 따로 띄워서, 그동안에도 다음 누름을 바로 받고 다시 누르면 복귀를 취소합니다. 측정 크기는 바꾸지 않으므로 옆 버튼이 밀리지 않습니다. 최소 70ms를 둔 이유는 스크롤 안 버튼 때문입니다. 빠르게 톡 치면 누름과 뗌이 거의 함께 와서 효과가 보이지 않았습니다. 글자 버튼은 가로로 많이 늘면 글자가 퍼져 보여 가로 늘림을 절반으로 줄였습니다.

2. 끊김: 중간에 멈춰도 끝 상태는 맞게

축하하던 호랑이가 공중에 멈췄다

기초 배우기 마지막 단계를 마치면, 징검다리 위의 호랑이가 펄쩍펄쩍 다섯 번 뜁니다. 그런데 뛰는 도중 다른 돌을 누르면 호랑이가 공중에 뜬 채 멈췄습니다. 마지막 돌로 돌아오면 축하를 처음부터 다시 했습니다.

원인은 LaunchedEffect의 취소였습니다. 축하는 “축하 중"이라는 값을 키로 한 효과 안에서 돌았고, 다른 돌을 고르면 키가 바뀌어 효과가 중간에 취소됩니다. 취소되면 animateTo 다음 줄은 실행되지 않습니다. 점프 값은 취소된 순간(공중)에 머물고, 맨 끝에 있던 “축하를 봤다” 기록도 실행되지 않았습니다.

정리할 일을 두 곳으로 나눈다

LaunchedEffect(celebrating) {
    if (!celebrating) { jump.snapTo(0f); landing.snapTo(0f); return@LaunchedEffect }
    try {
        repeat(FinishJumps) { /* 뛰고 내려앉기 */ }
    } finally {
        celebrated() // 끊겨도 축하는 한 번만
    }
}
  • 완료 기록은 finally에 둡니다. 끊겨도 본 것으로 남아 다시 돌아왔을 때 또 뛰지 않습니다.
  • 값 복구는 다음 실행의 시작에서 합니다. 키가 바뀌어 새로 시작한 효과가 snapTo(0f)로 호랑이를 바로 돌 위에 내려놓습니다.

둘을 나눈 이유가 있습니다. finally는 이미 취소된 코루틴 안이라, snapTo 같은 suspend 함수를 부르면 바로 취소 예외가 납니다. 새로 시작한 실행은 값을 바로 놓을 수 있습니다. withContext(NonCancellable)로 감싸는 방법도 있지만, 키가 바뀌면 새 실행이 어차피 시작되므로 그쪽에서 값을 놓는 편을 택했습니다.

3. 튕김: 짧게 튕겨도 펼침이 보이게

이 부분은 「조금 밀었을 뿐인데 홈 화면이 중간으로 순간이동했다」의 후속입니다. 그 글에서는 손을 뗄 때 관성이 멈출 곳으로 스냅 목표를 먼저 정하고, 손가락 속도를 이어받는 스프링 하나로 목표까지 가게 했습니다.

그 뒤 다른 문제가 보였습니다. 첫 화면에서 짧고 세게 튕기면 펼치는 과정이 거의 보이지 않았습니다. 관성이 펼침 구간(400dp)을 지나 카드 구간까지 닿으면 기본 관성으로 넘겼는데, 기본 관성은 펼침 구간을 몇 프레임 만에 지나갔습니다.

스프링도 이 경우에는 맞지 않았습니다. 스프링은 걸리는 시간이 손 속도에 따라 정해져 최소 시간을 보장할 수 없습니다. 빠른 속도에서는 목표를 지나치려는 값을 목표에서 잘라 멈추고 있었습니다.

그래서 펼침 구간 안에서 시작한 관성은 카드 구간까지 가더라도 펼친 화면에서 멈추게 했습니다. 앞 글의 ‘착지점이 400dp 이상이면 기본 관성’ 경계는 펼친 화면 이후에서 시작한 관성에만 남겼습니다. 그리고 스프링 대신, 시간을 0.45~0.55초로 정한 곡선으로 바꿨습니다. 손가락 속도는 곡선의 시작 기울기로 이어받습니다.

// 시작 기울기가 m이고 끝에서 멈추는 3차 곡선. m ≤ 3이면 목표를 지나치지 않는다.
Easing { u -> m * u * (1f - u) * (1f - u) + u * u * (3f - 2f * u) }

m을 손가락 속도 × 시간 / 거리로 정하면 놓는 순간의 속도가 끊기지 않습니다. 아무리 세게 튕겨도 최소 0.45초 동안 그림이 작아지고 제목이 올라가는 과정이 보입니다. 대신 빠르게 튕기면 기울기가 3에 막혀 놓는 순간 눈에 띄게 느려집니다. 예를 들어 남은 360dp를 6000dp/s로 튕기면 곡선의 시작 속도는 2400dp/s입니다. 목표를 지나쳤다 되돌아오는 것보다 낫다고 판단해 받아들였습니다.

확인한 것과 남은 것

  • 스냅 목표와 곡선 시간 계산은 단위 테스트로 고정했습니다.
  • 눌림 효과는 시스템의 ‘애니메이션 끄기’ 설정에서 어떻게 동작하는지 확인하지 않았습니다.
  • 축하 애니메이션의 끊김 처리는 자동 테스트 없이 코드 수정으로만 남아 있습니다.

세 가지 모두 “움직임이 끝났을 때 화면이 어떤 상태여야 하는가"를 먼저 정하는 작업이었습니다. 눌림은 신호가 되는 곳에만, 끊김은 끝 상태와 기록을 따로, 튕김은 손의 속도를 이으면서도 과정은 보이게 했습니다.
