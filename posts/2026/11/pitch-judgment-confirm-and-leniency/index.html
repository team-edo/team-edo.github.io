판정을 언제 보여 주고, 누구에게 너그러울 것인가

실시간 판정 색을 측정이 끝난 뒤에만 칠하도록 바꾸고, 대금의 한 옥타브 낮은 소리를 받아 주는 완화 규칙을 연습 화면과 기초 배우기가 함께 쓰게 만든 과정입니다.

이 글은 앞서 쓴 두 글의 후속입니다. 「지나간 음이 한꺼번에 틀림으로 바뀌던 실시간 채점」에서는 지나간 음의 판정 색을 고정했습니다. 「단소만 넘어가기 어려웠던 이유, 보이지 않는 빈 창」에서는 한 음씩 연습에 단소용 완화 규칙을 더했습니다.

두 기능을 쓰면서 각각 질문이 하나씩 더 생겼습니다. 판정 색은 언제 칠해야 바뀌지 않을까. 그리고 완화 규칙은 어디에 두어야 화면마다 기준이 달라지지 않을까. 구현은 AI 코딩 에이전트와 함께 했고, 저는 표시 방식과 적용 범위를 정했습니다.

1. 실시간 판정: 측정이 끝난 음만 칠한다

“두 음 앞"은 위치일 뿐 근거가 아니었다

앞 글의 고정 규칙은 “지금 음보다 두 음 앞까지 고정"이었고, 색은 진행 바가 칸을 다 지난 뒤에만 보였습니다. 그러면 바로 앞 음이 틈에 남습니다. 진행 바는 지나갔으니 색은 보이는데, 아직 고정 전이라 조율 추정이 바뀌면 색도 바뀔 수 있었습니다.

바뀔 수 있는 색을 보여 주는 것 자체가 문제라고 봤습니다. 그래서 질문을 바꿨습니다. 어느 위치까지 고정할지가 아니라, 그 음의 값이 더 이상 오지 않는 때가 언제인지를 기준으로 삼았습니다.

값이 더 오지 않는 두 가지 조건

판정 결과가 들어오는 길을 다시 보니 두 가지 경계가 있었습니다.

  • 녹음 입력 창은 그 창의 소리를 받은 시각에서 300ms 안에 처리된 것만 받습니다. 그러니 음이 끝나고 300ms가 지나면 그 음의 값은 더 오지 않습니다.
  • 판정 결과는 현재 음과 직전 음에만 붙습니다. 연주가 두 음 뒤로 넘어가면 그 음에 붙을 결과는 없습니다. 빠른 곡에서는 이쪽이 300ms보다 먼저 옵니다.

둘 중 먼저 오는 쪽에서 그 음의 판정을 확정합니다.

event.index <= position - 2 || run {
    val end = (event.startTick ?: return@run false) + (event.durationTick ?: return@run false)
    elapsedMs >= end * msPerTick + lateMs // lateMs = 300
}

확정한 음에는 늦게 온 값을 받지 않습니다. 연주 시계와 녹음 시계가 조금 어긋나 확정 뒤에 값이 오더라도 색은 바뀌지 않습니다.

화면에는 확정한 것만

화면은 확정한 음의 판정만 칠합니다. 진행 바가 지나갔어도 확정 전이면 비워 두고, 확정되는 순간 한 번 칠합니다. 칠한 뒤 연주가 한 음 더 넘어가면 맞음의 진한 연두를 옅은 연두로 가라앉힙니다. 방금 판정된 음만 눈에 띄고, 지나간 음은 배경으로 물러납니다.

같이 바꾼 것이 두 가지 있습니다. 판정 색을 운지법 보기에도 칠했고, 색 안내를 끌 수 있는 스위치를 더했습니다. 이 스위치는 처음에 연습 설정의 ‘실시간 채점’이었고, 이후 보기 설정을 정리하면서 연주 평가 화면 제목 줄의 ‘퍼펙트 스코어’ 버튼으로 옮겨졌습니다.

2. 한 음씩 판정: 완화 규칙을 한 곳에 모은다

같은 “한 음 불기"인데 화면마다 기준이 달랐다

QA 중에 한 음 불기 판정이 연습 화면의 ‘한 음씩’과 기초 배우기의 ‘직접 불기’ 두 곳에 따로 있다는 것이 드러났습니다. 단소용 완화는 연습 화면 쪽 코드에 있었고, 기초 배우기는 자기 판정 기준을 따로 쓰고 있었습니다. 같은 사용자가 같은 악기로 같은 음을 부는데, 화면에 따라 기준이 달랐던 셈입니다.

그래서 서버 기준 위에 얹는 앱 쪽 완화를 담던 값 객체를 공통 위치로 옮겨 두 화면이 함께 쓰게 했습니다.

data class StepLeniency(
    val gapMs: Int = 0,                 // 짧은 끊김 허용
    val gate: PitchGate = PitchGate.Default, // 높이 추정 문턱
    val wideFirstNote: Boolean = false, // 첫 음 넓게 받기
    val lowerOctave: Boolean = false,   // 한 옥타브 낮은 소리 받기(대금, 아래에서 더함)
)

두 화면 모두 악기 코드로 같은 객체를 받습니다. 단소와 두 대금만 완화하고, 소금은 서버 기준 그대로입니다.

대금은 한 옥타브 낮게 나기도 한다

대금도 맞게 불어도 다음 음으로 잘 넘어가지 않는다는 문제가 남아 있었습니다. 운영 녹음에서는 대금 소리가 악보보다 한 옥타브 낮게 나는 연주도 확인됐습니다. 서버 채점은 이런 음을 한 옥타브 올려 보도록 이미 고쳤지만, 기기 안의 한 음씩 판정은 옥타브가 다르면 다른 음으로 봤습니다.

그래서 대금에 단소 완화를 모두 적용하고, 공통 객체에 규칙 하나를 더했습니다. 목표보다 한 옥타브 아래 근처(−1,800센트 이상 −600센트 미만)의 소리는 1,200센트를 더해 목표 옥타브로 옮겨 잽니다.

fun foldLowerOctave(cents: Double): Double =
    if (lowerOctave && cents >= -1800 && cents < -600) cents + 1200 else cents

위로는 열지 않았습니다. 관찰된 것은 낮게 나는 연주뿐이고, 위까지 받으면 다른 옥타브 실수를 모두 맞음으로 보게 됩니다.

악기 특성과 학습 목적은 나눠 둔다

모든 차이를 이 객체에 넣지는 않았습니다. 기준이 다른 이유가 악기 때문인지, 그 단계의 학습 목적 때문인지 나눴습니다.

  • 기초 배우기 6단계는 새 음역을 실제로 내는지 보는 단계라서, 대금이라도 낮은 옥타브를 받아 주지 않습니다.
  • 4·5단계는 옥타브를 따지지 않습니다.
  • 3단계 ‘한 소리 길게 내기’는 기준을 통일할 때 한 음씩 유지 시간에 맞춰 0.3초로 줄였는데, 이름과 달리 금방 끝나 버렸습니다. 4단계 직접 불기와 같은 1초로 되돌렸습니다.

이런 예외는 객체 밖, 기초 배우기 쪽에서 정합니다. 화면의 ‘통과 기준’ 문구에 나오는 초는 판정에 쓰는 같은 상수에서 만들어서, 값을 바꾸면 문구도 함께 바뀝니다.

확인한 것과 남은 것

  • 실시간 판정: 확정 조건과 늦은 값 거부를 자동 테스트로 검사합니다. 실기기에서 확정 표시를 따로 확인하지는 않았습니다.
  • 대금 완화: 실제 대금 녹음 대신, 단소 녹음에서 잰 음별 높이를 반으로 낮춘 합성음을 판정기에 넣는 검증을 만들었습니다. 대금 완화로는 다섯 음이 모두 통과합니다. 같은 낮은 소리를 완화 없이 판정하면 넘어가지 않는다는 것은 별도 단위 테스트로 확인했습니다. 실제 대금 소리로는 아직 확인하지 않았습니다.
  • 대금 서버 기준(±70센트, 200ms)은 단소 값을 그대로 가져온 것이라 측정으로 정한 값이 아닙니다. 채점 기준을 맡은 팀원의 확인이 필요합니다.
  • 한 옥타브 아래만 받으므로, 곡 음역 안의 낮은 음으로 높은 목표를 대신해도 맞음이 됩니다. 서버 채점이 받아들인 것과 같은 선택입니다.

두 변경은 방향이 같습니다. 판정은 사용자가 믿고 따라가는 기준이라서, 한 번 보여 준 색이 바뀌거나 화면마다 기준이 달라지면 기능 전체를 의심하게 됩니다. 보여 주는 시점과 기준을 둘 곳을 정하는 일이 판정 공식만큼 중요했습니다.
