평가 버튼부터 총점까지, 앱과 서버 로그를 어떻게 연결했나

얼쑤의 연주 평가에서 앱과 서버가 각자의 단조 시계로 잰 시간을 진단 ID로 연결하고, 같은 조건의 실기기 표본으로 검증한 과정을 소개합니다.

얼쑤에서 연주를 마치고 평가하기를 누르면 앱은 연습 세션을 만들고 녹음을 올립니다. 서버는 분석을 작업 큐에 넣고, 앱은 상태를 조회하다가 완료 응답을 받으면 결과 화면을 엽니다. 버튼에서 총점까지 걸린 시간만으로는 녹음 전송에 시간이 걸렸는지, 분석 작업이 큐에서 기다렸는지, 결과가 준비된 뒤 앱에서 표시되기까지 시간이 걸렸는지 알기 어려웠습니다.

먼저 각 구간의 시작과 끝을 정했습니다. 그다음 같은 평가의 앱 로그와 서버 로그를 찾을 수 있도록 분석 시도마다 진단 ID를 붙였습니다.

앱과 서버에서 각각 경과 시간 재기

구간시작끝
앱의 제출부터 첫 총점까지평가 버튼 처리 중 분석 화면으로 이동하기 직전결과 화면이 총점을 처음 그린 직후
서버의 큐 대기분석 작업을 실행기에 넘기기 직전워커가 작업을 시작할 때
서버의 처리워커가 작업을 시작할 때결과 저장을 마치고 호출이 반환될 때

앱은 Kotlin의 TimeSource.Monotonic으로 실행 중인 프로세스 안에서 이벤트 시각을 기록합니다. 같은 실행과 제출에 속한 첫 총점 이벤트에서 제출 이벤트의 값을 빼면 화면까지의 경과 시간이 나옵니다. 종료점은 Compose가 총점을 처음 그린 시점입니다. 결과 화면으로 이동한 뒤에도 필요한 데이터를 읽고 총점을 그리는 데 시간이 걸릴 수 있어 그리기를 기준으로 삼았습니다.

서버는 System.nanoTime()으로 작업 제출, 워커 시작, 처리 종료의 차를 계산합니다. 처리 시간에는 세션 상태 조회, 악보 준비, 분석 서비스 호출, 결과 저장이 들어갑니다. 각 구간의 차는 같은 프로세스의 단조 시계에서 구했습니다. 서로 다른 기기의 시계 값을 빼면 두 시계의 기준점 차이까지 섞이기 때문입니다.

진단 ID로 같은 분석 시도 찾기

한 번 제출한 녹음은 실패한 뒤 다시 분석할 수 있습니다. 앱은 실행 ID와 제출 번호로 시작과 첫 그리기를 짝짓습니다. QA 앱은 녹음 업로드 요청에 무작위 진단 ID를 넣습니다. 서버는 새 분석을 예약할 때 이 ID를 시도 번호와 함께 저장하고, 워커는 같은 ID로 큐 대기와 처리 시간을 기록합니다. 앱은 상태 조회의 완료 응답에서 실제 시도의 ID를 읽어 완료 확인 이벤트에 남깁니다.

아래는 같은 정상 평가의 기록을 진단 ID A로 표시한 예입니다. 숫자는 비교에 포함된 병합 후 한 회차에서 얻었습니다.

기록 위치관측값
앱 · 제출 → 첫 상태 조회1.317초
앱 · 첫 상태 조회 → 첫 DONE 해석5.467초 · 진단 ID A
앱 · DONE 해석 → 총점 첫 그리기0.205초
서버 · 진단 ID A, 첫 시도 DONE큐 대기 기록값 0ms · 처리 4.725초

이 회차에서 제출부터 첫 총점까지는 6.989초였습니다. 서버 분석은 앱이 업로드 응답을 기다리는 동안 시작될 수 있어 두 쪽 구간이 겹칩니다. 서버 시간은 앱 시간과 따로 읽어야 합니다.

앱은 분석이 진행 중이면 조회 시작 후 처음 8초 동안 응답을 받은 뒤 최대 1초를 기다리고, 그 뒤에는 2초를 기다려 다음 상태를 조회합니다. 따라서 첫 조회부터 DONE 해석까지는 여러 HTTP 요청의 왕복과 조회 사이 대기가 모두 들어갑니다. 이 기록에서 서버가 완료한 시점부터 앱이 그 사실을 감지할 때까지의 별도 지연은 미측정입니다.

같은 서버 배포의 실기기 표본 비교

Galaxy S10(Android 12) 한 대에서 Wi-Fi와 동일한 승인된 QA 계정을 사용했습니다. 단소 아리랑 악보 판본 1, 48 BPM으로 두 앱을 교대로 실행했습니다. 녹음 완료 화면에서 같은 30초 합성 M4A로 녹음을 교체했고, 기기에서 파일 해시가 일치하는 것을 확인한 뒤 평가를 제출했습니다.

병합 후 정상 평가 7건 모두에서 앱의 업로드·완료 확인 로그를 서버의 첫 시도 DONE 한 건과 연결했습니다. 이 7건은 진단 ID가 실제 운영 흐름에서 이어졌는지 확인한 표본입니다. 병합 전 앱에는 서버 시도와 연결할 진단 ID가 없어 그쪽의 서버 구간은 미측정입니다.

앱의 전후 시간 비교에는 운영 백엔드의 커밋 SHA와 실행 슬롯이 모두 같은 3쌍을 사용했습니다. 측정 도중 백엔드 커밋이 바뀌었고, 같은 커밋이 다른 슬롯에서 실행된 구간도 있었습니다. 전환 구간과 다른 배포 조건의 회차를 빼서 두 앱이 같은 배포와 실행 슬롯을 사용한 표본으로 비교했습니다.

제출 → 총점 첫 그리기횟수중앙값범위
병합 전 앱37.215초6.947–7.652초
병합 후 앱36.989초6.860–7.548초

병합 후 중앙값은 226ms(3.1%) 낮았습니다. 비교에 들어간 병합 후 3건의 서버 큐 대기 기록값은 모두 0ms였고, 처리 시간은 4.725–4.951초였습니다. 앱 시간의 범위가 겹치고 표본이 버전별 3건이라 이 차이가 변경 때문에 생겼는지, 반복 측정에서도 유지되는지는 확인하지 못했습니다.

같은 녹음으로 다시 분석하면 진단 ID도 바뀐다

재시도에서는 앱의 제출과 서버의 분석 시도가 어떻게 달라지는지 확인했습니다. Galaxy S10의 마이크로 스피커에서 재생한 45초 합성음을 녹음했습니다. 격리된 Spring·MySQL 환경에서 로컬 분석 서비스 대역이 첫 분석 요청에 HTTP 503을 반환하도록 설정했습니다. 앱에서 분석 다시 시도를 누르면 대역은 두 요청이 같은 녹음 객체와 바이트를 읽었는지 확인한 뒤 두 번째 요청에 합성 성공 응답을 반환했습니다.

세 회차 모두 최초 업로드의 진단 ID A가 서버 첫 시도의 SERVER_ERROR에 연결됐습니다. 재시도에서 새로 접수된 진단 ID B는 앱의 재시도 응답과 완료 확인, 서버의 attempt=2 DONE에 남았고, 총점이 표시됐습니다. 같은 녹음 한 건에서도 진단 ID가 달라져야 어느 분석이 실패했고 어느 분석이 결과를 만들었는지 찾을 수 있습니다.

서버가 B를 접수했는데 앱이 응답을 받지 못할 수도 있습니다. B의 작업이 진행 중일 때 앱이 새 후보 ID C로 요청하면 서버는 already-pending과 기존 B를 돌려줍니다. 앱 호스트 테스트는 응답 유실과 중복 응답을 대역으로 재현해 앱이 완료를 B에 연결하는지 확인했습니다. MySQL HTTP 통합 테스트에서는 중복 요청이 새 작업을 만들지 않고 기존 ID를 반환하는 것을 확인했습니다.

버튼 처리 지점을 기록하는 이벤트를 추가한 임시 앱에서 재시도 버튼부터 첫 총점까지 중앙값은 1.341초, 범위는 0.517–1.481초였습니다. 서버 큐 대기 기록값은 3건 모두 0ms였고, 처리 시간은 중앙값 54ms, 범위 40–64ms였습니다. 재시도 수치는 단일 앱 빌드와 로컬 분석 서비스 대역을 쓴 격리 환경에서, 정상 평가와 다른 시작점으로 측정했습니다. 운영 분석 서비스의 재시도 시간과 TIMEOUT 경로는 미측정입니다.

이 계측으로 같은 분석의 서버 처리와 사용자가 기다린 앱 구간을 한 회차에서 함께 볼 수 있게 됐습니다. 상태 조회 간격을 조정할 근거를 얻으려면 서버 완료부터 앱 감지까지의 지연을 별도로 재야 합니다.
