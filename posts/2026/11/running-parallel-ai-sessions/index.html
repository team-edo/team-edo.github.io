AI 세션 여러 개로 개발하며 배운 운영법

AI 코딩 세션 여러 개를 동시에 돌리며 작업을 나누는 기준, develop에 빠진 작업을 찾는 방법, 설치와 검증의 구분, Windows 워크트리 정리, 세션 사이 인계에서 배운 것을 정리했습니다.

권영민·2026.11.13
이 글의 목차
  • 1. 화면이 아니라 파일로 나눈다
  • 2. 끝난 줄 안 작업이 develop에 없을 때
  • 3. 설치했다와 검증했다는 다르다
  • 4. Windows에서 워크트리 정리가 반만 된다
  • 5. 세션의 기억은 그 세션에만 있다
  • 남은 과제

얼쑤의 프론트엔드는 Claude Code 데스크톱 앱에서 AI 세션 여러 개를 동시에 띄워 만들었습니다. 한 세션이 요청 목록을 받아 묶음을 나누고 하위 세션을 엽니다. 하위 세션은 각자 최신 develop에서 만든 워크트리와 브랜치에서 구현·검증·MR까지 진행합니다. 저는 나누는 방식을 정하고, 결과를 확인하고, 병합을 맡았습니다.

세션 수를 늘리는 것 자체는 쉬웠습니다. 어려웠던 것은 세션 사이의 경계였습니다. 같은 파일, 공용 기반, 공유 에뮬레이터, 끝난 줄 알았던 작업, 세션마다 따로 있는 기억이 그 경계에서 문제를 일으켰습니다. 그때마다 정한 운영 방식을 다섯 가지로 정리합니다.

1. 화면이 아니라 파일로 나눈다

처음에는 요청을 화면 단위로 나누면 된다고 생각했습니다. 실제로 기준이 된 것은 ‘같은 파일을 고치는가’였습니다. 한 번은 화면 수정 요청 10개를 받아 다음처럼 나눴습니다.

요청묶은 방식이유
연주 결과 회색 바탕, 연습 기록 저장 모달 정리한 세션둘 다 같은 결과 화면 파일을 고침
틀린 유형 탭 바 디자인따로 한 세션, 고칠 파일을 탭 바 컴포넌트 하나로 한정화면 하나의 요청이지만 네 화면이 함께 쓰는 컴포넌트
나머지 화면별 요청화면 파일마다 한 세션서로 겹치는 파일 없음

화면이 달라도 한 파일을 함께 고치면 순서를 정했습니다. 기초부터 배우기의 가로 화면은 왼쪽 목록과 오른쪽 상세를 한 배치 파일에서 그립니다. 상세를 고치는 작업과 목록을 고치는 작업은 동시에 하지 않고 한 흐름 안에서 이어서 했습니다. 문자열 리소스나 내비게이션 정의처럼 여러 세션이 어쩔 수 없이 함께 고치는 파일은 각자 자기 항목 근처만 최소로 고치고, Push 직전에 develop을 다시 받게 했습니다.

공용 기반은 텍스트 충돌보다 중복이 더 컸습니다. 두 사람이 각자 작업하다 소리 재생 인터페이스가 이름만 다르게 두 개 생긴 적이 있습니다. HTTP 클라이언트를 들일 때는 세션이 먼저 멈춰서 물었습니다. 제 작업에 HTTP 클라이언트가 필요했는데, 라이브러리 선택과 네트워크 모듈 구성이 다른 팀원 작업 범위에 들어 있었기 때문입니다. 둘이 같은 버전 카탈로그와 빌드 파일, 네트워크 모듈을 동시에 만들면 충돌도 나고 구조도 갈라집니다. 세션이 정리해 준 범위 나눔으로 팀원과 조율해 제가 맡기로 하고 시작했습니다. 그 뒤에도 연습 시간 기록을 보내는 대기열과 HTTP 클라이언트가 둘 다 401에서 토큰을 갱신하고 있어서, 401 한 번에 갱신을 두 번 시도하지 않도록 갱신을 클라이언트 한 곳으로 모았습니다.

동시에 돌릴 흐름 수는 컴퓨터 사양으로 정하지 않았습니다. 이 PC는 메모리 64GB, 논리 CPU 22개라 더 돌릴 수 있었지만 세션은 두 흐름을 권했습니다. 세 흐름부터는 제가 리뷰하고 실기기로 확인하는 일이 병목이 된다는 이유였습니다. 다만 문구·여백처럼 작은 수정을 여러 개 맡길 때는 그보다 많은 세션을 한꺼번에 열기도 했습니다. 그리고 이것은 이 프로젝트에서 제 확인 속도에 맞춘 판단이지, 흐름 수를 바꿔 가며 잰 결과는 아닙니다.

공유 자원은 순번을 정했습니다. 에뮬레이터는 한 대를 여러 세션이 함께 쓰므로 잠금 파일을 두었습니다.

  • 설치 전에 잠금 파일을 봅니다. 15분이 안 된 파일이 있으면 다른 세션이 화면을 확인하는 중이니 최대 20분 기다립니다.
  • 비어 있으면 자기 세션 이름을 적고, 설치하고, 화면을 확인한 뒤 파일을 지웁니다.
  • 화면을 볼 때마다 자기 브랜치 APK를 다시 설치합니다. 지금 깔린 앱이 자기 빌드라고 가정하지 않습니다.
  • 로그인이 풀리지 않게 adb install -r로 덮어 설치하고 앱 데이터는 지우지 않습니다.

마지막으로 보고 방식입니다. 지휘 세션이 하위 세션에 보낸 메시지는 대기열에 들어갈 뿐이라, 하위 세션이 언제 읽었는지 알 수 없습니다. 그래서 끝난 뒤 보고에서 “브랜치 6개가 원격에 Push된 것은 직접 확인했고, MR 상태는 각 세션의 보고를 옮긴 것"처럼 출처를 나눠 적게 했습니다. 화면 확인도 MR마다 따로 적었습니다. 그때 MR 하나는 에뮬레이터 마이크로 소리가 들어가지 않아 평가 결과 화면을 열지 못했고, 테스트와 빌드만 통과한 상태로 ‘화면 미확인’이라고 적어 넘겼습니다.

2. 끝난 줄 안 작업이 develop에 없을 때

연습 평가 화면의 박자 표시를 장구 아이콘으로 바꾼 적이 있는데, develop에 없었습니다. 확인해 보니 그 작업은 이 앱의 세션이 아니라 다른 AI 코딩 도구에서 했습니다. 이미 병합된 Task의 후속 브랜치에 커밋 5개를 쌓았지만 Push하지 않아 MR이 열리지 않았습니다. 그 시간에는 Jira 연결도 인증 오류(401)로 실패해서 기록이 남지 않았습니다.

다른 경우도 있었습니다. 단소의 한 음씩 판정 기준을 완화한 작업은 커밋이 하나도 없이 워크트리에 파일 16개를 고친 상태로만 남아 있었습니다.

이런 일은 한 단계씩 판정하면 끊긴 곳이 바로 보였습니다.

단계확인끊긴 사례
작업 트리git -C <워크트리> status --porcelain판정 기준 완화: 커밋 0개, 수정 파일 16개
커밋git rev-list --count origin/develop..<브랜치>장구 아이콘: develop에 없는 커밋 5개
Pushgit ls-remote --heads origin <브랜치>장구 아이콘: 원격 브랜치 없음
내용 반영git cherry origin/develop <브랜치>커밋별 patch-id로 같은 변경이 들어갔는지 봄

git cherry는 커밋마다 비교하므로, 여러 커밋을 하나로 합쳐(squash) 병합한 변경은 들어갔어도 미반영으로 보일 수 있다고 생각합니다. 직접 확인한 동작은 아닙니다.

장구 브랜치는 develop보다 234커밋 뒤처져 있어서, 그대로 합치면 홈·곡 목록·연습 화면 파일 19개가 충돌할 상황이었습니다. 그래서 브랜치를 통째로 합치지 않았습니다. 원래 Task는 이미 완료로 닫혀 있어 새 Task를 만들고, 최신 develop에서 새 브랜치를 만든 뒤 필요한 커밋만 옮겼습니다.

  • 5개 중 악기 선택 위치를 옮긴 커밋은 그사이 다른 작업으로 develop에 들어가 있어서 뺐습니다.
  • 사진형 장구와 일러스트 장구 두 커밋은 최종 일러스트 하나로 합쳤습니다.
  • 충돌한 곳은 develop에 새로 생긴 휴대폰 배치를 살리고, 옛 변경은 넓은 화면에만 적용했습니다.

옮긴 뒤 공통 테스트(Android 1,160개, Wasm 1,136개)와 빌드가 통과했습니다. 그래도 살려 낸 옛 작업은 그사이 병렬로 진행된 작업과 다시 부딪힐 수 있었습니다. 실제로 옮긴 작업의 문구 삭제가 다른 진행 중 작업과 충돌했습니다.

장구 커밋이 남아 있었던 것은 워크트리를 정리할 때 브랜치마다 develop에 없는 커밋이 있는지 먼저 확인하고, 있는 워크트리는 지우지 않았기 때문으로 보입니다.

3. 설치했다와 검증했다는 다르다

세션이 “실기기에서 확인했다"고 보고해도, 어떤 코드로 빌드한 APK를 어느 서버에 붙여 확인했는지 모르면 검증 범위를 착각합니다. 실제로 겪은 함정은 이렇습니다.

  • 에뮬레이터를 켜는 것과 앱을 설치하는 것은 다릅니다. Android Studio의 Device Manager에서 ▶를 누르면 에뮬레이터만 켜집니다. 앱은 마지막에 설치된 것, 예를 들어 다른 워크트리에서 빌드한 것이 그대로 남아 있습니다. 메인 체크아웃이 origin/develop보다 1,288커밋 뒤처져 있던 때도 있어서, 거기서 Run을 눌러도 옛 코드가 설치됐습니다.
  • 버전으로 빌드를 구분할 수 없었습니다. versionCode가 고정이라 모든 빌드의 버전이 같습니다. 대신 dumpsys package의 lastUpdateTime과 APK 파일의 수정 시각을 비교했습니다. 에뮬레이터의 시각은 UTC로 나옵니다.
  • installDebug는 연결된 모든 기기에 설치합니다. 한 기기에만 넣으려면 adb -s <시리얼> install -r을 씁니다. 반대로 휴대폰 USB가 끊긴 상태면 에뮬레이터에만 설치하고도 성공으로 끝납니다.
  • 앱과 서버를 함께 바꾼 변경은 서버까지 맞춰야 합니다. 판정 기준 완화는 서버 설정(허용 오차 50센트 → 70센트, 유지 시간 300ms → 200ms)과 앱 로직을 함께 바꿨습니다. 그런데 실기기에 깐 APK는 운영 서버에 붙어 있어서 서버 쪽 완화는 적용되지 않았고, 화면의 맞음 범위 띠도 ±50센트로 보였습니다. 그 확인은 앱 쪽 절반만 검증한 것이었습니다.
  • 덮어 설치한 뒤에는 앱을 강제 종료하고 다시 실행해야 새 빌드가 보입니다.

반대 경우도 있습니다. 에뮬레이터 확인 전에 MR이 먼저 병합된 적이 있는데, 확인한 APK가 병합된 커밋으로 빌드한 것과 같은 코드라는 점을 확인하고 그 검증을 유효하다고 봤습니다.

그래서 기기 확인 보고에는 네 가지를 꼭 넣게 했습니다. 어느 커밋으로 빌드했는지, 어느 기기에 설치했는지, 설치 시각, 어느 서버에 붙었는지입니다.

4. Windows에서 워크트리 정리가 반만 된다

병합이 끝난 세션을 앱에서 보관해도 워크트리 폴더는 남았습니다. 그래서 git worktree remove로 직접 지웠는데, Windows에서는 이것이 반만 되는 일이 잦았습니다. 한 번은 워크트리 22개와 로컬 브랜치 19개를 한꺼번에 정리했는데, 이때를 포함해 여러 번 같은 순서로 막혔습니다.

  1. Gradle build/ 아래 경로가 너무 길어 “Filename too long"으로 실패합니다.
  2. 다시 시도하면 “is not a working tree"가 나옵니다. 첫 시도에서 git 등록은 이미 풀렸고 폴더만 남았다는 뜻입니다. 이제는 git이 아니라 파일 시스템으로 지워야 합니다.
  3. 남은 폴더는 긴 경로를 허용하는 \\?\ 접두사로 지웁니다(cmd /c rd /s /q "\\?\<절대 경로>"). 이 명령에 변수를 넣었다가 변수가 비면 드라이브 루트를 가리킵니다. 실제로 그런 명령을 자동 권한 검사가 막은 적이 있습니다.
  4. 빈 폴더가 “Device or resource busy"로 남으면 그 폴더를 작업 디렉터리로 잡고 있는 상주 프로세스를 의심합니다. 워크트리 안에서 띄운 Kotlin 컴파일 데몬, Gradle 데몬, adb 서버가 원인이었습니다. ./gradlew --stop과 adb 종료 뒤 지워졌습니다. 다만 다른 세션이 빌드하는 중이면 데몬을 멈추지 않고 빈 폴더를 그냥 두었습니다.

브랜치 정리에도 함정이 있었습니다. git branch -d는 지금 체크아웃한 HEAD에 병합됐는지로 판단하므로, 메인 체크아웃의 로컬 develop이 낡아 있으면 이미 병합된 브랜치도 거부합니다. origin/develop에 들어 있는지 확인한 뒤 -D로 지웠습니다.

워크트리를 만들 때 지킨 것도 두 가지 있습니다. 폴더 이름은 영문과 숫자로 지었습니다. 경로에 한글이 있으면 Gradle 동기화가 실패했습니다. 새 워크트리에는 Android SDK 경로를 적은 local.properties가 없어서 메인 체크아웃에서 복사했습니다.

5. 세션의 기억은 그 세션에만 있다

세션 둘이 각자 ‘공유 노트 폴더’에 인계 노트를 남겼다고 보고했는데, 저장소와 워크트리 어디에도 없었습니다. 찾아보니 이 계정의 앱 데이터 폴더에 있었습니다. 다른 계정에서는 보이지 않는 위치입니다. 자동 메모리에 쌓아 둔 규칙도 같은 이유로 다른 계정에서 이어받을 수 없다고 보고 움직였습니다. 다만 메모리가 계정 단위로 묶인다는 것은 이 경험에서 추론한 것이고, 다른 내용보다 근거가 약합니다.

다른 계정에서 이어 갈 수 있게 인계서를 따로 썼습니다. 원칙은 그 문서 하나만 읽고 시작할 수 있어야 한다는 것이었습니다.

  • 먼저 알 것: 이슈 관리 계정과 담당자 지정 방법, 스프린트 종료 시각, 최신 와이어프레임 위치, 메인 체크아웃이 낡았다는 사실
  • 합의된 작업 방식: Task별 워크트리, local.properties 복사, 커밋·MR은 요청할 때만, 다른 Task Key를 커밋에 적지 않기
  • 끝난 Task와 남은 Task, 그 사이의 의존 관계와 이미 정한 결정
  • 이전 세션 인계 노트와 메모리 내용의 요약
  • 열려 있는 문제와 지금 있는 워크트리 목록
  • 나중에 다시 쓴 인계서에는 다른 팀원의 진행 중인 큰 브랜치와 겹치는 지점, 담당이 비어 있는 일도 넣었습니다

쓰면서 두 가지를 더 챙겼습니다. 인계서도 그 시점의 문서라서, 기준이 된 develop 커밋을 적지 않으면 다음 사람이 낡은 상태를 믿게 됩니다. 또 AI 도구와 이슈 관리 도구가 다른 팀원 계정으로 연결돼 있으면 작성자와 담당자가 섞이므로, 그 사실을 인계서 앞부분에 적었습니다. 스킬도 다른 세션의 기록을 알아서 읽지 않습니다. 필요한 세션에서 직접 부르거나, 읽을 기록을 지정해 줘야 합니다.

남은 과제

  • 나누는 기준은 사람이 봐야 합니다. 같은 파일을 고치는지는 세션이 코드를 읽고 판단하지만, 공용 기반의 주인이 누구인지는 팀 합의라서 세션이 정할 수 없었습니다.
  • 흐름 수는 측정하지 않았습니다. 적절한 흐름 수는 제 리뷰 속도에 맞춘 판단입니다. 리뷰와 실기기 확인을 나눠 맡는 사람이 늘면 달라질 수 있습니다.
  • 검증 보고 형식. 커밋·기기·시각·서버를 적는 것을 보고 양식으로 고정하지는 않았습니다.

AI 세션을 여러 개 띄우면 여러 작업을 동시에 진행할 수 있었습니다. 대신 경계마다 생기는 빈틈을 사람이 메워야 했습니다. 나누기 전에 파일을 보고, 끝난 뒤에는 단계별로 확인하고, 넘길 때는 문서로 남기는 것이 그 빈틈을 줄이는 방법이었습니다.
