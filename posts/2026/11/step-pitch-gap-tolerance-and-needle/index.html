단소만 넘어가기 어려웠던 이유, 보이지 않는 빈 창

한 음씩 연습에서 단소만 유독 넘어가기 어려웠던 원인을 높이를 못 구한 창에서 찾고, 짧은 끊김을 봐주는 규칙과 흔들리지 않는 음높이 바늘을 만든 과정입니다.

권영민·2026.11.13

이 글은 앞서 쓴 「맞는 음을 불어야 넘어가는 연습, 기기 안에서 판정하기」의 후속입니다. 그 글에서는 혼자 연습 화면의 ‘한 음씩 따라 불기’에 휴대폰 안 음높이 판정을 붙였습니다. 목표 음에서 ±50센트 안의 높이가 300ms 끊기지 않고 이어지면 맞음으로 봅니다.

이번에는 그 판정을 쓰면서 들어온 피드백 두 가지를 다룹니다. 하나는 “단소가 소금보다 넘어가기가 너무 어렵다"였고, 다른 하나는 진단용 음높이 바늘이 “너무 불안정하게 움직인다"였습니다. 둘 다 제가 직접 써 보고 남긴 피드백입니다. 구현은 AI 코딩 에이전트에게 맡기고, 저는 방향을 정하고 실기기에서 확인했습니다.

판정기에는 모두 ‘높이 없음’으로 보인다

처음에는 소리가 작아서 그런 줄 알았습니다. 코드를 따라가 보니 크기 하나의 문제가 아니었습니다. 판정기에 “이 창은 높이가 없다"로 똑같이 들어오는 원인이 세 가지 있었습니다.

원인조건어디서
크기 관문창의 RMS가 −45dBFS보다 작으면 높이를 구하지 않음YIN 추정기
주기 관문YIN 정규화 차이가 0.15보다 작은 주기가 없으면 높이를 구하지 않음(김 소리·잡음)YIN 추정기
대기열 넘침분석 대기열(4창, 약 80ms)이 차면 비우고 ‘분석 불가’ 창 하나를 넣음Android 녹음기

300ms 유지 규칙에서는 이 셋이 모두 같은 결과를 냅니다. 창 하나만 비어도 유지 시간을 처음부터 다시 셉니다. 20ms 간격이면 약 17개 창이 하나도 빠지지 않고 이어져야 맞음이 됩니다.

원인을 눈으로 가르려고 디버그 빌드에만 보이는 음높이 막대를 만들었습니다. 막대에서 ‘소리 작음’과 ‘주기 불명확’을 나눠 보이게 했습니다. 두 경우를 합쳐 ‘소리 없음’으로만 보이면, 작아서인지 김 소리 때문인지 알 수 없었기 때문입니다.

이 과정에서 하나를 더 알게 됐습니다. 서버 기준에는 신뢰도 하한 0.8이 있는데, 이 기준에 걸리는 창은 사실상 나오지 않습니다. 추정기가 정규화 차이 0.15 미만일 때만 높이를 주므로, 신뢰도(1 − 차이)는 늘 0.85를 넘습니다. 주기 선명도는 서버 기준보다 추정기의 문턱이 더 엄격하게 거르고 있었습니다.

빈 창이 얼마나 자주 끼면 막히는가

앞서 실측 높이로 만든 재생 테스트가 있었습니다. 실제 단소·소금 녹음에서 잰 음별 높이로 합성음을 만들고, Android 녹음기와 같은 창(2,048샘플)·간격(882샘플, 약 20ms)으로 판정기에 넣는 테스트입니다. 판정 기준은 서버 기본값(±50센트, 300ms)이고, 여기에 일정 간격으로 분석 불가 창을 끼워 넣었습니다.

경우결과(음 시작부터 통과까지)
단소 평취 그대로5음 모두 0.3~0.4초
단소, 25창(0.5초)마다 분석 불가 1창5음 모두 0.4~0.6초
단소, 15창(0.3초)마다 분석 불가 1창하나도 통과 못 함
소금 평취 그대로(목표보다 +53~+83센트)첫 음에서 멈춤

0.3초마다 빈 창 하나면, 300ms를 다 채우기 직전에 매번 0으로 돌아갑니다. 맞게 불어도 영원히 넘어가지 않습니다.

흥미로운 점은 깨끗한 합성음에서는 단소가 잘 넘어가고 소금이 막혔다는 것입니다. 실제로는 반대였습니다. 그렇다면 합성음에서 뺀 것, 즉 김 소리·떨림·작은 소리가 원인일 가능성이 큽니다. 단소는 입김을 취구에 대고 부는 악기라 김 소리 비중이 크다고 봤습니다. 다만 이것은 추정입니다. 실제 단소 녹음으로 어느 관문에 몇 번 걸렸는지는 세어 보지 않았습니다.

고친 방법: 단소에만 짧은 끊김을 봐준다

단소 곡에만 세 가지 완화를 넣었습니다. 소금과 대금은 서버 기준 그대로입니다. 단소인지는 악보의 악기 코드로 정합니다.

val Danso = StepLeniency(gapMs = 100, gate = PitchGate.Lenient, wideFirstNote = true)

fun forInstrument(code: String?): StepLeniency = if (code == "DANSO") Danso else Strict

짧은 끊김 허용(gapMs). 마지막으로 맞은 창부터 100ms 안의 끊김은 유지를 다시 세지 않습니다. 높이 없음뿐 아니라 높이 미확정, 잠깐 범위 밖으로 흔들린 창도 포함합니다. 봐준 시간도 유지 시간에 들어갑니다.

private fun breakRun(reading: PitchReading) {
    if (run.isEmpty()) return
    val gap = (reading.endSample - lastInRangeEnd) * 1000.0 / reading.sampleRate
    if (leniency.gapMs > 0 && gap <= leniency.gapMs) return
    run.clear()
}

기준점이 중요합니다. 끊긴 순간이 아니라 마지막으로 맞은 창의 끝에서 잽니다. 그래서 끊김이 길어지면 결국 지워집니다. 테스트에서는 3창(60ms) 빈 뒤 다시 불면 유지가 이어지고, 6창(120ms)이 비면 처음부터 다시 셉니다.

높이 추정 문턱 완화. 한 음씩을 듣는 동안만 크기 관문을 −55dBFS로, 주기 관문을 0.2로 낮춥니다. 멈추면 기본값으로 되돌립니다. 다른 화면의 음높이 분석은 바뀌지 않습니다.

첫 음 넓게 받기. 앞선 글에서 첫 음은 조율 보정을 재는 음이라 보정 없이 판정된다고 썼습니다. 그래서 악기 전체가 낮으면 시작에서 막혔습니다. 단소는 첫 음 조율 전에 범위를 넓힙니다. 곡에서 목표 바로 위·아래 음까지 거리의 절반과 조율 상한 중 작은 값까지 받습니다. 이웃 음과 헷갈리지 않는 범위에서만 넓히는 것입니다.

같은 작업에서 서버의 단소 기준값도 바꿨습니다. 허용 오차를 50에서 70센트로, 유지 시간을 300에서 200ms로, 조율 상한을 50에서 100센트로 늘렸습니다. 이 값들은 실기기 피드백으로 정했고 측정으로 확정한 값이 아닙니다. 그래서 채점 기준을 맡은 팀원의 확인을 요청해 두었습니다.

바늘이 너무 흔들렸다

막대로 원인을 보려던 참에 다른 피드백이 생겼습니다. 바늘이 너무 불안정하게 움직여서 읽기 어려웠습니다. 막대의 문구도 모두 빼기로 했습니다.

흔들림의 원인을 다섯 가지로 나눴습니다. 한 창만 튀는 값, 창마다 바늘이 옮겨 가는 것, 값이 불안정한 창, 짧은 끊김에 바늘이 깜빡이는 것, 첫 음 조율 뒤 눈금 자체가 바뀌는 것입니다.

판정은 원래 값 그대로 두고, 화면에 그리는 바늘만 세 단계로 다듬었습니다.

val cents = gauge.cents?.takeIf { gauge.state in NeedleStates } ?: return null
recent.push(cents)
val middle = recent.sorted()[(recent.size - 1) / 2]
val next = smoothed?.let { it + follow * (middle - it) } ?: middle
smoothed = next
return next
  1. 최근 3창 중앙값. 한 창짜리 튐을 버립니다. 창이 둘뿐이면 작은 쪽 값을 써서, 새 값 하나로는 바늘이 옮겨 가지 않게 했습니다.
  2. 지수 평균(follow 0.3). 남은 작은 떨림을 줄이며 천천히 따라갑니다.
  3. 스프링 애니메이션. 그 위에 Compose 스프링을 걸어 미끄러지듯 움직이게 했습니다.

나머지도 하나씩 막았습니다. 높이 미확정·신뢰도 낮은 창은 바늘에 쓰지 않습니다. 높이 없음이 0.25초 안이면 바늘을 제자리에 두고, 그보다 길면 흐려지게 했습니다. 눈금은 허용 오차의 두 배(최소 ±100센트)로 고정하고 맞음 띠의 너비만 바뀌게 했습니다. 그래야 값은 그대로인데 눈금이 바뀌어 바늘이 움직여 보이는 일이 없습니다.

대가도 있습니다. 다듬은 바늘은 판정보다 잠깐 늦습니다. 바늘은 띠 안에 있는데 판정은 아직 맞음이 아닌 순간이 생길 수 있습니다. 이 막대는 디버그 빌드에만 나오는 진단 도구라 그 차이를 받아들였습니다.

확인한 결과와 한계

  • 단소 완화 테스트 8개와 바늘 다듬기 테스트 5개를 추가했습니다. 완화 테스트에는 소금이 기존 기준 그대로인지도 들어 있습니다.
  • 재생 테스트의 수치는 합성음 결과입니다. 실제 김 소리·떨림·마이크 특성은 들어 있지 않습니다.
  • 단소 완화를 넣은 빌드를 Galaxy S25에 설치했지만, 그때 앱은 운영 서버에 붙어 있었습니다. 서버 기준값 완화는 아직 반영 전이었습니다. 첫 음 넓게 받기도 서버의 조율 상한(그때 50센트)까지만 넓히므로 효과가 없었고, 짧은 끊김 허용과 문턱 완화만 적용된 상태였습니다.
  • 완화 뒤 얼마나 쉬워졌는지, 다듬은 바늘이 실제로 덜 흔들려 보이는지는 체감 기록을 남기지 않았습니다. 설치한 뒤 다른 작업으로 넘어갔습니다.
  • 단소가 어려운 원인을 김 소리로 본 것은 추정입니다. 실제 녹음으로 관문별 횟수를 세지 않았습니다.

남은 과제

  • 관문별 횟수 세기. 실제 단소 연주에서 크기 관문, 주기 관문, 대기열 넘침이 각각 몇 번 걸리는지 로그로 세어 봐야 완화 폭이 적당한지 말할 수 있습니다.
  • 대기열 넘침 확인. 운지 그림이 많은 화면에서 분석 스레드가 밀리는지는 실기기 로그로 아직 보지 않았습니다.
  • 다른 악기. 대금은 재생 테스트를 하지 않았습니다. 소금은 합성음에서 첫 음부터 막혔으니 따로 살펴봐야 합니다.
  • 기준값 합의. 단소 서버 기준값은 측정으로 다시 정해야 합니다.

“N ms 동안 끊김 없이"라는 규칙은 단순해 보이지만, 무엇이 끊김인지를 정하는 쪽에 함정이 있었습니다. 원인이 다른 결측이 판정기에는 똑같이 보였습니다. 원인을 나눠 보이게 만든 것이 출발점이었습니다.
