프론트가 안 붙인 API를 찾다가 두 번 틀린 이야기

명세서의 연결 상태 대신 배포 서버의 OpenAPI 문서와 프론트 코드를 대조해 미연결 API를 찾았고, 그 결과가 두 번 틀린 이유와 이후 정한 점검 절차를 정리했습니다.

“지금 프론트가 연결하지 않은 API가 뭐야?” 얼쑤 개발 중반에 제가 AI 코딩 에이전트에게 여러 번 던진 질문입니다. 간단해 보이지만, 처음 받은 답 “6개입니다"는 그중 2개가 틀렸습니다. 이 글은 어디서 틀렸는지와, 그 뒤로 미연결 API를 판정할 때 쓰는 절차를 정리합니다.

조사와 대조는 AI 코딩 에이전트가 했고, 저는 결과를 보고 범위를 정하고 틀린 곳을 되짚었습니다.

명세서의 상태 칸은 쉽게 낡는다

팀은 API 명세서에 API마다 ‘FE 연결’ 상태 칸을 둡니다. 처음에는 이 칸만 보면 될 줄 알았습니다. 그런데 명세서를 develop 코드와 비교해 보니 맞지 않는 줄이 여럿 나왔습니다.

방향예
명세서는 ‘FE 연결 전’, 코드는 이미 호출비밀번호 재설정, 간편 로그인 가입, 간편 로그인 재인증 탈퇴
명세서는 ‘FE 연결 전’, 코드는 이미 사용내 정보 응답의 비밀번호 보유 여부
명세서는 ‘API 시작 전’·‘진행 중’, 백엔드는 이미 develop에 있음내 악보, 학습 진도, 연습 기록

상태 칸은 사람이 손으로 바꾸는 값이라, 코드가 병합돼도 저절로 따라오지 않습니다. 그래서 상태 칸은 참고만 하고, 판정은 실제로 배포된 서버와 실제 코드로 하기로 했습니다.

OpenAPI 경로와 코드 경로 문자열을 대조한다

방법은 단순합니다.

  1. 배포 서버의 OpenAPI 문서를 받아 메서드와 경로를 모두 뽑는다. 77개였습니다.
  2. 최신 origin/develop의 프론트 코드에서 따옴표로 감싼 API 경로 문자열을 뽑는다.
  3. 두 목록을 메서드·경로로 맞춘다.

로컬 체크아웃이 아니라 origin/develop을 본 이유가 있습니다. 다른 기능의 연결 상태를 확인할 때 제 로컬 develop은 원격보다 1,158커밋 뒤처져 있었습니다. 로컬 기준으로 판정하면 이미 끝난 일을 미연결로 셉니다.

대조 결과 코드에 없는 경로는 10개였습니다. 그중 4개는 처음부터 앱이 부를 일이 없는 API라 따로 뺐습니다.

  • 카카오가 서버로 보내는 웹훅
  • 서버 안의 악보 인식기만 쓰는 내부 API
  • iOS 간편 로그인의 리다이렉트 콜백
  • 서명된 녹음 읽기 주소

남은 6개를 “프론트에 연결이 빠진 API"로 보고했습니다. 악보 변환 상태 조회, 변환 재시도, 음표별 오류 조회, 한 음씩 연습 판정 기준, 기본음 음원 상세, 버전별 약관 문서입니다. 나머지 67개는 같은 경로와 메서드로 호출하고 있었습니다.

틀림 1: 서버가 준 주소를 그대로 여는 경우

연결 작업을 시작하면서 버전별 약관 문서 API가 이미 쓰이고 있다는 것을 알았습니다. 약관 동의 화면은 서버의 약관 목록 응답에 든 문서 주소(contentUrl)를 받아, 그 주소로 바로 요청합니다.

suspend fun loadDocument(contentUrl: String): List<TermsBlock>? {
    if (!isHttpsDocumentUrl(contentUrl)) return null
    // 문서 주소는 text/html만 내준다. 공통 클라이언트는 JSON만 받겠다고 보내 406이 나므로 HTML을 받겠다고 밝힌다.
    val response = client.sendOrNull { get(contentUrl) { accept(ContentType.Text.Html) } } ?: return null

코드 어디에도 /terms/documents/...라는 문자열이 없습니다. 경로는 런타임에 서버가 정합니다. 문자열 검색은 이런 호출을 볼 수 없어서 “미연결"로 잘못 셌습니다.

돌아보면 힌트는 처음 보고에 이미 있었습니다. 서명된 녹음 읽기 주소를 따로 빼면서 “서버가 응답으로 준 주소를 앱이 그대로 재생하는 방식으로 보이는데, 코드에서 확인하지는 않았다"고 적었습니다. 같은 모양의 호출이 약관에도 있을 수 있다는 생각을 그때 하지 못했습니다.

틀림 2: 조사하는 사이 develop이 움직였다

한 음씩 연습 판정 기준 API도 보고 시점에는 호출하는 곳이 없었습니다. 그런데 이 API를 붙이려고 작업 폴더를 만들고 최신 develop을 다시 보니, 한 음씩 판정기가 이미 들어와 있었습니다. 다른 작업 세션이 같은 기능을 구현하고 있었고, 제 작업 폴더에도 제가 쓰지 않은 변경이 생겼습니다. 한 작업 폴더를 두 AI가 동시에 고치면 안 되기 때문에 그쪽 세션에 확인 메시지를 보내고 손을 뗐습니다. 그 기능은 대조 기준으로 삼은 develop 커밋보다 약 한 시간 반 늦게, 같은 날 오전에 병합됐습니다.

이건 잘못 읽은 게 아니라 답이 만료된 경우입니다. 대조는 맞았지만, 그 결과가 몇 시간 만에 사실이 아니게 되었습니다. 이후 결과에는 항상 어느 커밋 기준인지 적고, 작업을 시작하기 직전에 한 번 더 받아 보기로 했습니다.

결국 이 작업에서 6개 중 새로 붙인 것은 악보 변환 상태 조회와 재시도뿐이었습니다. 음표별 오류 조회는 지금 쓰는 평가 응답으로 부족한 점이 있는지부터 봐야 했고, 음원 상세는 쓰는 화면이 없어 둘 다 범위에서 뺐습니다. ‘내가 동의한 약관 버전 보기’는 앱만으로 만들 수 없었습니다. 내 정보 응답이 동의한 버전을 돌려주지 않아서, 백엔드 계약을 바꿔야 하는 일이었습니다.

붙인 API도 ‘연결됨’이 ‘동작함’을 뜻하지는 않았습니다. 당시 배포 서버는 원본 파일을 보관하지 않아 변환 재시도가 항상 거절됐습니다. 그래서 화면에서 실제로 보이는 버튼은 ‘다시 시도’가 아니라 ‘다시 불러오기’였습니다.

반대 방향의 빈틈: 경로는 있는데 등록은 예시

두 번 틀린 것은 모두 ‘연결됐는데 미연결로 센’ 쪽이었습니다. 반대 방향의 빈틈도 있습니다. 경로 문자열은 코드에 있는데, 앱이 실제로는 그 구현을 쓰지 않는 경우입니다.

얼쑤 프론트는 초반에 API 없이 와이어프레임대로 화면부터 만들었습니다. 저장소 인터페이스 뒤에 예시 데이터를 돌려주는 구현을 Koin에 등록해 두고, API가 생기면 등록만 바꾸는 전략이었습니다. 화면과 ViewModel은 데이터가 어디서 오는지 모르니 고치지 않아도 됩니다. 실제로 교체는 이렇게 한 줄이었습니다.

-    single<PracticeRecordRepository> { UnavailablePracticeRecordRepository() }
+    single<PracticeRecordRepository> { HttpPracticeRecordRepository(get(), get()) }

이 전략 덕분에 API를 기다리지 않고 화면을 진행할 수 있었습니다. 그 대가로 ‘구현이 있다’와 ‘앱이 그 구현을 쓴다’가 다른 문제가 됐습니다. 앞서 명세서와 코드를 비교할 때도, 백엔드에는 연습 기록 API가 다 있는데 앱의 DI에는 Unavailable… 구현이 등록돼 있어 기록 저장·목록·재생·삭제가 모두 동작하지 않았습니다. 내 악보도 Sample… 구현이라 앱을 끄면 사라졌습니다.

이 두 경우는 해당 경로 문자열이 아직 코드에 없어서 문자열 대조로도 미연결로 잡혔습니다. 하지만 HTTP 구현 클래스를 먼저 만들어 두고 등록 교체를 빠뜨리면, 문자열 대조는 “연결됨"이라고 답합니다. 이번에 77개를 대조한 시점의 DI에는 API 저장소 중 예시 구현이 남아 있지 않아 이 빈틈 때문에 틀리지는 않았습니다. 경로가 있는데 등록이 예시로 남은 실제 사례도 찾지 못했습니다. 그래도 전략상 생길 수 있는 빈틈이라 절차에 넣었습니다.

지금 쓰는 점검 절차

  1. 상태 칸은 출발점으로만 쓴다. 명세서의 ‘FE 연결’ 상태로 판정하지 않는다.
  2. 배포 서버의 OpenAPI 문서에서 메서드·경로를 뽑는다. 앱이 상대하는 것은 배포된 서버다.
  3. 최신 origin/develop의 경로 문자열과 맞춘다. 로컬 체크아웃은 낡았을 수 있다. 기준 커밋을 결과에 적는다.
  4. 서버끼리 쓰는 API를 뺀다. 웹훅, 내부 API, OAuth 콜백처럼 앱이 부르지 않는 것.
  5. 못 찾은 경로는 서버가 준 주소로 여는지 본다. 응답의 …Url 필드를 그대로 요청하거나 재생하는 코드를 찾는다.
  6. 찾은 경로는 DI 등록을 본다. 그 경로를 부르는 구현이 실제로 등록돼 있는지, Sample…·Unavailable…이 남아 있지 않은지 확인한다.
  7. 작업 시작 직전에 다시 받는다. 보고와 착수 사이에도 develop은 움직인다.
  8. 경로 일치는 화면 동작의 증명이 아니다. 실제 호출과 화면 확인은 따로 한다.

5번과 6번이 이번에 배운 것입니다. 문자열 대조는 ‘코드에 적힌 것’만 보므로, 런타임에 정해지는 주소와 런타임에 정해지는 구현은 따로 확인해야 합니다. 취약 구간 기능의 연결 상태를 확인할 때는 앱이 두 API를 호출하는 구현이 있다는 것에 더해, DI에 그 구현이 실제로 등록돼 있다는 것까지 근거로 남겼습니다.

남은 과제

  • 녹음 읽기 주소. 앱은 녹음 조회 응답의 재생 주소를 그대로 씁니다. 그 주소가 서명된 녹음 읽기 API인지는 서버 응답으로 확인하지 않았습니다.
  • 명세서 상태 칸. 낡은 줄을 찾아냈지만, 병합할 때 상태 칸을 함께 고치는 습관이 자리 잡지 않으면 같은 일이 반복됩니다.
  • 동적 주소 찾기. 5번은 응답 필드 이름에 기대는 검색이라, 이름이 …Url 꼴이 아니면 빠뜨릴 수 있습니다.

“연결 안 된 API"라는 질문에는 사실 세 가지가 섞여 있었습니다. 코드에 호출이 있는가, 앱이 그 코드를 실제로 쓰는가, 그리고 그 답이 언제 기준인가입니다. 셋을 나눠 확인하고 나서야 숫자를 믿을 수 있게 됐습니다.
