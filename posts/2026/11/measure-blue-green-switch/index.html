블루그린 전환이 끊기지 않았는지 어떻게 확인했을까

얼쑤의 블루그린 최초 설치와 버전 전환을 나눠 보고, 실제 HTTP 요청과 컨테이너 상태로 확인한 범위를 소개합니다.

우동균·2026.11.09

배포 도구에 성공 표시가 뜬 뒤에도 궁금한 점이 남았습니다. 백엔드를 새 버전으로 연결하는 순간, 사용자 쪽 요청에도 응답이 돌아왔을까요? 얼쑤에서는 운영 주소에 같은 요청을 반복해 이 구간을 관측했습니다. 블루그린은 한 자리가 응답하는 동안 다른 자리에서 새 버전을 준비하는 방식입니다. 얼쑤의 블루그린 배포 구조

최초 설치와 이후 전환을 나눴습니다

처음에는 기존 구성에 두 실행 자리와 연결 규칙을 추가해야 했습니다. 이때 일부 서비스를 다시 시작했고, API 요청 실패가 약 36초 동안 관측됐습니다. 두 자리를 마련한 뒤에는 운영 중인 서비스를 같은 방식으로 다시 시작할 필요 없이 새 자리로 연결을 넘겼습니다. 최초 설치에서 본 실패 시간과 이후 버전 전환의 요청 결과는 각 단계에서 따로 기록했습니다.

전환 전후 같은 질문을 반복했습니다

운영 주소에 백엔드 준비 상태와 약관 읽기를 반복해서 요청했습니다. 배포 작업의 결과만 볼 때와 달리, 이 방식으로는 전환 시각 전후에 그 두 종류의 요청이 성공했는지 셀 수 있습니다.

확인한 작업관측한 결과
블루그린 구성의 최초 적용API 요청 실패가 약 36초 동안 관측됐습니다.
블루에서 그린으로 전환관측한 241건이 모두 HTTP 200이었습니다.
그린에서 블루로 전환관측한 168건이 모두 HTTP 200이었습니다. Nginx와 MySQL 컨테이너의 ID도 유지됐습니다.

최초 적용과 이후 전환은 작업 자체가 달라 36초와 요청 성공 건수를 같은 조건의 전후 비교로 볼 수는 없습니다. 241건과 168건은 전환 때 보낸 두 종류의 읽기 요청에 한정됩니다. 로그인, 녹음 업로드, 긴 채점 작업이 같은 조건에서 이어졌는지는 이 수치로 알 수 없습니다.

운영에서 같은 검사를 하려면 요청을 전환 전에 시작하고, 전환이 끝난 뒤까지 시각과 응답을 기록해 둡니다. 결과를 공유할 때는 성공 건수 옆에 어떤 요청을 몇 번 보냈는지도 적습니다. 업로드 연속성이 중요하다면 파일을 보내는 중에 전환하는 시험을 따로 해야 그 기능에 대한 근거가 생깁니다.
