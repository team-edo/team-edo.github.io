따로 받은 페이지 목록을 앱에서 합칠 때 그어야 하는 기준선

악기별로 나뉘어 오는 연습 기록을 서버 API를 바꾸지 않고 앱에서 한 곡으로 합치면서, 아직 받지 않은 기록 때문에 순서가 비지 않도록 기준선 규칙을 정한 과정입니다.

얼쑤의 연습 기록 화면은 저장한 연주를 곡별로 묶어 보여 줍니다. 그런데 같은 ‘비행기’를 단소로 한 번, 소금으로 한 번 불면 ‘비행기’ 묶음이 두 개 생겼습니다. 저는 곡 하나에 묶음 하나를 두고, 그 안에서 연습한 날짜별로 연주를 모아 보이게 하고 싶었습니다.

구현은 AI 코딩 에이전트와 함께 했습니다. 저는 ‘같은 곡’의 기준과 화면 동작을 정하고, 실제 계정으로 화면을 확인했습니다. 이 글은 그중 가장 헷갈렸던 부분, 따로 페이지를 받는 목록 여러 개를 한 줄의 시간순으로 합치는 규칙을 정리합니다.

왜 갈라져 보였나

서버의 곡별 요약 조회는 기록을 song_id, 제목, 악기 코드로 묶습니다. 얼쑤에서는 같은 곡이라도 악기마다 곡 ID가 다릅니다. 그래서 ‘비행기’는 단소용 ID와 소금용 ID, 두 묶음으로 내려옵니다. 앱도 묶음을 곡 ID 기준으로 다루고 있었습니다.

묶음 안의 기록은 곡 ID마다 따로 받습니다. 한 번에 20개씩, 페이지 번호로 다음 묶음을 요청합니다.

서버를 바꿀지, 앱에서 합칠지

구현 전에 정해야 할 것이 세 가지였습니다.

질문정한 것
같은 곡의 기준악기와 관계없이 합친다. 대신 기록마다 악기 그림과 이름을 붙여 구분한다
날짜 드롭다운의 기본 상태곡을 펼치면 날짜도 모두 펼친다(처음엔 맨 위 날짜만 펼쳤다가 바꿨다)
데이터 범위서버 API와 명세는 그대로 두고, 앱이 받은 페이지를 합친다

세 번째가 핵심 선택이었습니다. 처음부터 곡의 모든 날짜를 보여 주려면 서버가 악기를 넘어 곡을 묶고 날짜 목록을 따로 내려줘야 합니다. API 계약을 바꾸고 명세서도 같이 고쳐야 하는 일입니다. 앱에서 합치면 서버는 건드리지 않아도 됩니다.

대가로 받아들인 제약은 하나입니다. 기록이 많으면 오래된 날짜는 ‘더 보기’를 누른 뒤에 나옵니다. 이 제약을 알고 앱에서 합치기로 했습니다.

같은 곡의 기준은 제목입니다. 앞뒤 공백만 무시하고 제목이 같으면 한 묶음입니다. 제목이 비어 있으면 곡 ID로 따로 둡니다.

private fun groupKey(song: RecordSongSummary): String = song.title.trim().ifEmpty { "#${song.songId}" }

‘곡명 · 소금1’처럼 제목에 다른 글자가 붙은 곡은 따로 묶입니다. 이 경우는 이번 범위에서 다루지 않았습니다.

그냥 합치면 생기는 구멍

두 목록을 받아서 합치고 시간 역순으로 정렬하면 될 것 같지만, 한 목록에 다음 페이지가 남아 있으면 문제가 생깁니다. 테스트에 넣은 예시로 보겠습니다. 날짜는 모두 11월입니다.

곡 ID받은 기록다음 페이지
단소 비행기d2(12일 10시), d1(11일 20시)남음
소금 비행기s2(12일 8시), s1(10일 9시)없음

그대로 합치면 d2, s2, d1, s1 순서가 됩니다. 그런데 단소의 다음 페이지에 11일 오후나 10일 기록이 있을 수 있습니다. 그 기록은 d1과 s1 사이에 들어가야 합니다. 화면은 10일 연주가 하나뿐인 것처럼 보이다가, ‘더 보기’를 누르면 중간에 기록이 끼어듭니다. 날짜별로 접어 보여 주는 화면이라 ‘11월 10일 · 1회’ 같은 날짜 머리글 자체가 틀린 정보가 됩니다.

기준선 규칙

그래서 기준선을 둡니다. 다음 페이지가 남은 목록마다 지금까지 받은 마지막 기록의 시각을 보고, 그중 가장 최근 시각을 기준선으로 삼습니다. 기준선보다 오래된 기록은 아직 보여 주지 않습니다.

fun records(group: RecordSongGroup): List<PracticeRecord> {
    val loaded = group.songIds.mapNotNull { id -> pages[id]?.takeIf { it.loaded } }
    if (loaded.size < group.songIds.size) return emptyList()
    val ordered = loaded.flatMap { it.records }.distinctBy { it.id }
        .sortedWith(compareByDescending<PracticeRecord> { it.recordedAtMillis }.thenByDescending { it.id })
    val edge = loaded.filter { it.nextPage != null }.maxOfOrNull { it.records.last().recordedAtMillis } ?: return ordered
    return ordered.filter { it.recordedAtMillis >= edge }
}

규칙을 풀어 쓰면 이렇습니다.

  • 다음 페이지가 끝난 목록은 기준 계산에서 뺀다. 더 올 기록이 없으니 구멍을 만들지 않습니다. 모든 목록이 끝났으면 기준선 없이 전부 보여 줍니다.
  • 기준선은 남은 목록 중 가장 최근의 마지막 기록이다. 위 예시에서는 단소의 d1(11일 20시)이 기준선이 되고, 화면에는 d2, s2, d1만 나옵니다. s1(10일)은 단소를 더 받은 뒤에 보입니다.
  • 한 곡이라도 첫 페이지를 못 받았으면 묶음을 비워 둔다. 그 곡의 기록이 어디에 끼어들지 모르기 때문에 순서가 틀린 목록을 먼저 보여 주지 않습니다.
  • 합칠 때 id로 중복을 한 번 더 지운다. 페이지를 이어 붙일 때도 같은 처리를 합니다.

처음에 헷갈렸던 것은 ‘가장 최근’과 ‘가장 오래된’ 중 어느 쪽이냐였습니다. 다음 페이지가 남은 목록이 두 개라고 해 보겠습니다. A의 마지막 기록은 11월 10일 14시, B의 마지막 기록은 11월 8일입니다. 가장 오래된 쪽(8일)을 기준으로 삼으면 9일 기록까지 보여 주게 되는데, A는 10일 14시 이전 기록을 아직 하나도 받지 않았습니다. 9일에 A 기록이 있었다면 빠진 채로 보입니다. 가장 최근 쪽(10일 14시)을 기준으로 삼아야 그 위쪽은 모든 목록이 빠짐없이 받은 구간이 됩니다.

‘더 보기’는 곡 묶음 단위로 동작합니다. 누르면 그 묶음 안에서 다음 페이지가 남았거나 받기에 실패한 곡 ID를 모두 이어 받습니다. 기준선은 받을 때마다 아래로 내려갑니다.

접은 날짜를 저장하는 이유

묶음을 펼치면 날짜도 모두 펼쳐진 채로 시작하고, 누른 날짜만 접힙니다. 처음에는 펼친 날짜를 저장했는데, 이렇게 하면 ‘더 보기’로 새로 생긴 날짜는 집합에 없어서 접힌 채로 나타납니다. 사용자가 접은 적도 없는 날짜가 닫혀 있는 셈입니다.

그래서 사용자가 직접 접은 날짜만 곡 묶음별로 기억하게 바꿨습니다.

fun isDayOpen(group: RecordSongGroup, epochDay: Long): Boolean = epochDay !in closedDays[group.key].orEmpty()

기본값이 ‘펼침’이면 저장할 것은 예외인 ‘접음’뿐입니다. 이렇게 하면 나중에 생긴 날짜도 저절로 기본값을 따릅니다. 악기 필터를 바꾸면 펼친 묶음과 접은 날짜를 함께 비웁니다.

정렬도 하나로 줄였습니다. 한때 ‘오래된 순’ 토글을 넣었다가, 묶음 안은 항상 최신순으로 보기로 정하고 정렬 상태와 그 정렬에만 쓰던 요청을 함께 지웠습니다. 지금 서버에는 늘 최신순으로만 요청합니다.

확인한 것

RecordListGroupingTest에 다음을 넣었습니다.

  • 제목이 같은 곡은 악기와 관계없이 한 묶음이 되고, 기록 수와 최고 점수는 곡들을 합친 값이다.
  • 두 악기의 기록이 시각 순서대로 섞이고 날짜별로 나뉜다.
  • 위 예시처럼 다음 페이지가 남은 곡이 있으면 기준선 아래 기록을 숨긴다.
  • 한 곡이라도 첫 페이지를 받기 전이면 아무것도 보이지 않는다.
  • 날짜는 모두 펼쳐진 채로 시작하고, 누른 날짜만 접혔다가 다시 펼쳐진다.

작업 당시 공유 모듈 테스트(Android 호스트) 1,453개가 통과했고 4개는 건너뛰었습니다. MR 직전 develop을 합친 뒤에는 1,466개가 통과했습니다.

화면은 웹(Wasm) 개발 빌드를 실제 계정에 붙여 확인했습니다. 휴대폰 크기(375×812)에서 ‘아리랑’ 묶음이 녹음 11개, 최고 96점으로 하나로 모였고, 11월 10일을 펼치면 단소와 소금 기록이 시각 순서대로 섞여 나왔습니다. 각 줄에는 악기 그림과 이름이 붙어 있었습니다. 제목이 다른 ‘도라지타령’과 ‘단소 연습곡 1’은 따로 묶였습니다. 태블릿 가로(1280×800) 두 칸 배치에서는 왼쪽 목록이 같은 구조로 보이고 오른쪽에 가장 최근 기록이 열렸습니다.

다만 이 계정의 ‘아리랑’ 기록은 곡 ID마다 20개를 넘지 않아서, 기준선이 실제로 기록을 숨기는 장면은 화면에서 보지 못했습니다. 그 동작은 단위 테스트로만 확인했습니다.

남은 과제

  • 기록이 많은 계정에서의 확인. 곡 하나에 20개가 넘는 계정으로 ‘더 보기’ 전후에 날짜가 이어지는 모습을 봐야 합니다.
  • iOS와 Android 실기기. 이번에는 웹 빌드로만 화면을 봤습니다.
  • 제목이 조금 다른 곡. 제목에 다른 글자가 붙으면 따로 묶입니다. 같은 곡으로 볼지는 아직 정하지 않았습니다.
  • 낡은 주석. isDayOpen 위에 ‘맨 위 날짜만 펼친다’는 예전 규칙 설명이 한 줄 남아 있어 정리해야 합니다.

서버가 주는 단위와 화면이 원하는 단위가 다를 때, 앱에서 합치는 것은 생각보다 싸게 끝났습니다. 대신 ‘받은 것’과 ‘아직 모르는 것’의 경계를 화면에 그대로 드러내지 않도록 기준선 하나를 지켜야 했습니다.
