나중에 보낼 기록에는 주인을 적어 둔다

기기에 쌓아 두었다가 서버로 보내는 연습 시간 기록과 학습 진도를 다른 회원 계정으로 보내지 않도록, 로그아웃 처리 대신 데이터마다 주인을 적는 방식으로 정리한 과정입니다.

권영민·2026.11.13

얼쑤 앱에는 서버로 바로 보내지 못하고 기기에 잠시 남겨 두는 데이터가 두 가지 있습니다. 하나는 연습 시간 기록입니다. 악보 화면에서 연습한 구간을 기기에 쌓아 두었다가, 연결되면 서버로 보냅니다. 다른 하나는 ‘기초부터 배우기’ 완료 표시입니다. 서버에 학습 진도 API가 생기기 전에는 기기에만 저장했고, 지금은 그 표시를 서버로 옮겨야 합니다.

둘 다 같은 위험이 있습니다. 기록을 만든 회원과 보내는 순간 로그인한 회원이 다르면, A의 연습 시간이 B의 계정에 쌓입니다. 이 글은 그 위험을 어떻게 막았는지에 대한 이야기입니다. 측정 방식은 다루지 않고, 기록이 누구의 것인가만 봅니다.

구현은 AI 코딩 에이전트와 함께 했고, 저는 방식을 고르고 결과를 확인했습니다.

로그아웃할 때 지우면 되지 않을까

처음 떠오르는 방법은 로그아웃할 때 대기열을 비우는 것입니다. 실제로 로그아웃에는 ‘남은 기록을 한 번 보내 보고 지운다’는 처리가 이미 있었습니다.

문제는 회원이 바뀌는 길이 로그아웃 버튼만이 아니라는 점입니다.

  • 세션이 만료된 뒤 다른 회원이 로그인한다.
  • 앱이 종료된 상태에서 회원이 바뀌고, 다음 실행에서 대기열을 보낸다.
  • 탈퇴하면 서버가 로그인 쿠키를 지운다.

세션 만료나 앱 재실행에는 ‘지금 회원이 바뀐다’는 알림을 받을 지점이 없습니다. 경로마다 정리 호출을 붙이는 방식은 하나만 빠뜨려도 다른 회원의 인증으로 기록이 나갑니다. 새 로그인 경로가 생길 때마다 이 목록도 늘어납니다.

기록마다 주인을 적는다

그래서 방향을 바꿨습니다. 정리 시점을 쫓는 대신, 저장할 때 기록에 측정한 회원을 적고 보낼 때 지금 회원과 비교합니다. 서버의 로그인 응답에는 이미 userId가 들어 있었는데, 앱이 읽지 않고 있었습니다. 로그인에 성공하면 이 값을 기기에 남기는 SignedInMember를 만들었습니다.

연습 시간을 재는 측정기는 회원을 모르게 두었습니다. 회원은 대기열이 저장할 때만 붙입니다. 보낼 때의 판단은 이렇습니다.

지금 로그인한 회원기록의 주인동작
모름누구든보내지 않고 남겨 둔다
AA보낸다
AB보내지 않고 지운다. 오류 로그를 남긴다
A빈 값(측정할 때 회원을 몰랐음)다른 회원으로 보고 지운다
val status = member.whileSignedIn { current ->
    when (current) {
        null -> SIGNED_OUT
        item.memberId -> api.post(item.segment)
        else -> OTHER_MEMBER
    }
}
when (status) {
    SIGNED_OUT, null, 401 -> return@withLock
    OTHER_MEMBER -> {
        logError("다른 회원의 연습 시간 기록이라 보내지 않고 지움: ${item.segment.key}")
        remove(item.segment.key)
    }

같은 회원이 세션 만료 뒤 다시 로그인하면, 그동안 남겨 둔 기록을 그대로 보냅니다. 앱이 갑자기 꺼져 닫지 못한 구간도 열린 상태와 함께 회원을 저장해 두므로, 다음 실행에서 원래 회원으로 판단합니다. 회원 칸이 없는 예전 저장 형식의 줄은 읽지 않습니다. 주인을 모르는 기록은 아무에게도 보내지 않는다는 원칙을 형식 변경에도 그대로 적용했습니다.

로그아웃 처리는 지우지 않았습니다. 로그아웃하면 지금도 한 번 보내 보고 남은 기록을 지웁니다. 다만 이제 안전이 이 처리에 기대지 않습니다. 정리를 빠뜨려도 주인이 다른 기록은 보내는 순간 걸러집니다. 탈퇴는 서버가 쿠키를 지우므로 ‘보내 보고 지우기’가 아니라 ‘보내지 않고 지우기’입니다.

순서도 맞춰야 한다

주인을 비교해도 타이밍이 어긋나면 샐 수 있습니다. 대기열이 A의 기록을 보내려는 순간 B가 로그인해 쿠키가 바뀌면, 요청은 A로 판단했는데 B의 쿠키로 나갑니다.

그래서 로그인·로그아웃과 개별 HTTP 요청이 같은 Mutex를 쓰게 했습니다. 위 코드의 whileSignedIn은 잠금 안에서 지금 회원을 읽고 요청까지 보냅니다. 로그인 상태가 바뀔 때마다 세대 번호도 올려, 같은 회원이 다시 로그인한 경우도 이전 로그인과 구별합니다. 작업을 시작할 때의 세대와 지금 세대가 다르면 그 작업은 취소됩니다.

전제가 실제로 깨졌다

이 설계에는 전제가 하나 있습니다. 로그인 상태를 바꾸는 모든 경로가 SignedInMember를 갱신해야 합니다. 처음 MR을 올릴 때 리뷰 요청에도 “간편 로그인·가입 직후 로그인·탈퇴 API를 붙일 때 이 회원 값도 갱신해야 한다"고 적어 두었습니다.

얼마 뒤 그 전제가 깨진 것을 발견했습니다. 이메일 회원가입이 성공하면 서버는 로그인 쿠키를 함께 발급합니다. 사용자는 가입 직후 로그인된 상태입니다. 그런데 앱은 가입 응답의 userId를 저장하지 않았습니다. 쿠키는 있는데 앱이 아는 회원은 비어 있었습니다.

결과는 두 가지였습니다. 연습 세션을 만드는 요청은 회원을 모르면 보내지 않게 되어 있어 항상 실패했습니다. 연습 시간 기록은 ‘회원 모름’이라 대기열에 그대로 남았습니다. 회원 귀속 규칙이 오히려 정확하게 동작해서 막힌 셈입니다.

고치기 전에 먼저 실패하는 테스트를 만들었습니다. 기존 가입 성공 테스트에 회원 값 단언 하나를 더했습니다.

// 가입 201은 로그인 쿠키를 함께 주므로 다시 로그인하지 않아도 회원별 요청(연습 세션·연습 시간)을 보낼 수 있어야 한다.
assertEquals("42", member.id)

수정 전에는 expected:<42> but was:<null>로 실패했습니다. 버그를 테스트가 재현한다는 것을 확인한 뒤, 가입이 201을 받으면 간편 가입과 같은 방식으로 userId를 저장하게 고쳤습니다. 가입 요청도 로그인과 같은 잠금 안에서 보내고, 진행 중인 로그아웃이 있으면 끝날 때까지 기다리게 했습니다. 그렇지 않으면 로그아웃이 새로 받은 쿠키를 지울 수 있기 때문입니다. 가입이 실패한 경우에는 회원 값이 바뀌지 않는다는 단언도 함께 넣었습니다.

학습 진도 이관에도 같은 원칙

기초부터 배우기 완료 표시는 서버 학습 진도 API가 생기면서 기기에서 서버로 옮겨야 했습니다. 여기에도 같은 질문이 있습니다. 이 기기에 남은 완료 표시는 누구의 것인가.

기기 저장 키를 회원별로 나눴습니다. 회원 구분 없이 저장하던 예전 공용 키는 남겨 두되 어느 회원에게도 올리지 않습니다. 그 기기에서 다른 사람이 표시한 진도가 섞여 있을 수 있어서입니다.

// 회원을 가리지 않던 예전 공용 키는 보존하되 어느 회원에게도 올리지 않는다.
private fun key(trackId: String): String? = if (member == null) "learn_done_$trackId"
    else member.id?.let { "learn_done_member_${it.length}_${it}_$trackId" }

옮기는 시점은 앱 시작이 아니라 그 악기의 진도를 처음 불러올 때로 미뤘습니다.

  • 서버 목록을 먼저 받고, 서버에서 아직 미완료인 단계만 올린다.
  • 올리기에 성공한 단계만 기기에서 지운다. 실패한 단계는 남겨 다음에 다시 올린다.
  • 서버에 없는 단계 번호는 올릴 곳이 없으니 버린다.
  • 올릴 표시가 있을 때만 잠금을 잡는다. 마이페이지처럼 여러 악기 진도를 한꺼번에 받는 화면이 서로 막히지 않게 하기 위해서다.

이관 뒤의 완료 표시 토글은 화면을 먼저 바꾸고 서버에 저장합니다. 저장은 saveLock으로 하나씩 보냅니다. 빠르게 ‘완료’와 ‘취소’를 연달아 누르면 두 요청이 거꾸로 도착해 서버가 반대 상태로 남을 수 있기 때문입니다. 저장이 실패하면 화면 표시를 되돌리고 안내합니다.

학습 진도 이관재설치·다른 기기, 계정 분리, 중복 완료·해제, 일부 업로드 실패 후 재시도, 오프라인을 다룬 학습 테스트 56개가 Android 호스트와 Wasm 양쪽에서 통과

연습 시간 대기열의 회원 판단과 가입 직후 회원 저장은 테스트로만 확인했습니다. 실제 기기에서 세션 만료 뒤 다른 계정으로 로그인하는 시나리오, 이메일로 가입한 직후 바로 연습 녹음이 시작되는지는 이번 작업 기록 안에서 확인하지 못했습니다. iOS도 확인하지 않았습니다.

남은 과제

  • 새 로그인 경로. 이 방식은 ‘로그인 상태를 바꾸는 모든 경로가 회원 값을 갱신한다’에 기댑니다. 가입 버그가 바로 그 전제가 깨진 경우였습니다. 로그인 방식이 늘어날 때마다 회원 값 갱신을 테스트로 고정해야 합니다.
  • 남겨 둔 공용 키. 회원 구분 없던 예전 완료 표시는 지우지도 올리지도 않고 남아 있습니다. 언제 정리할지는 정하지 않았습니다.
  • 실기기 시나리오. 회원이 바뀌는 경로별로 실제 앱에서 대기열이 어떻게 처리되는지 확인해야 합니다.

정리하면, 나중에 보낼 데이터에는 만든 사람을 같이 적어 두는 편이 정리 시점을 빠짐없이 찾는 것보다 단단했습니다. 주인을 모르는 데이터는 누구에게도 보내지 않는다는 규칙 하나로 연습 시간과 학습 진도를 같은 방식으로 다룰 수 있었습니다.
