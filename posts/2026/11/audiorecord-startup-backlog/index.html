녹음을 시작하자마자 '연주가 중단되었어요'가 뜬 이유

AudioRecord를 막 시작했을 때 장치 위치가 앱이 읽은 양보다 크게 앞서는 현상을 입력 유실로 오판해 평가 녹음이 끊기던 문제를 측정으로 확인하고 고친 과정입니다.

얼쑤의 AI 연주 평가는 연주를 녹음해 서버로 보내 채점합니다. Android에서는 같은 마이크 입력으로 연주 중 실시간 음높이 안내도 만듭니다. 그런데 어느 날 평가 연주를 시작하자마자 ‘연주가 중단되었어요’가 떴습니다. 녹음이 시작되자마자 실패 처리된 것입니다.

이 글은 그 원인을 측정으로 확인하고 고친 기록입니다. 구현과 측정은 AI 코딩 에이전트와 함께 했고, 저는 증상을 알리고 방향을 정했습니다.

처음에 의심한 곳은 틀렸다

증상을 본 직전에 평가 중 악보 따라가기를 고친 작업이 있었습니다. 그래서 처음에는 그 수정을 의심했습니다. 원인은 그보다 앞서 실시간 음높이 기능을 만들 때 녹음기에 넣은 검사였습니다.

그 전에도 신호가 있었습니다. 악보 따라가기를 에뮬레이터에서 재현할 때, 녹음이 이 검사에서 바로 끊겼습니다. 그때는 에뮬레이터만의 문제로 보고 재현하는 동안 검사를 로컬에서 꺼 두었습니다. 같은 검사가 실제 증상의 원인이었습니다.

녹음기가 한 검사

Android 녹음기는 읽기마다 AudioRecord.getTimestamp로 입력 장치가 잡은 위치(framePosition)를 받습니다. 이 위치와 함께 오는 시각으로 녹음 샘플 위치를 기기의 단조 시계에 맞춥니다. 실시간 음높이 안내가 이 시각 기준을 씁니다.

검사는 이 위치가 앱이 읽은 양보다 버퍼 이상 앞서면 입력을 잃어버린 것으로 보고 녹음 전체를 실패 처리했습니다.

check(timestamp.framePosition <= fileSamples - segmentStart + count + input.bufferSizeInFrames) {
    "Microphone input overrun"
}

검사의 전제는 이랬습니다. 앱이 제때 읽고 있다면 장치 위치가 읽은 양보다 버퍼 이상 앞설 수 없고, 앞섰다면 버퍼가 넘쳐 프레임이 버려졌다는 뜻이라는 것입니다.

시작 직후의 값을 재 봤다

정말 입력을 잃었는지 보려고 임시 로그를 넣어 재 봤습니다. 측정 환경은 이렇습니다.

  • Windows, Android API 37 에뮬레이터, 호스트 마이크 켬
  • 디버그 APK, 평가 곡은 구아리랑
  • 44.1kHz, 한 번에 882프레임씩 읽기, 클라이언트 버퍼 3,528프레임
시점장치 위치(framePosition)앱이 읽은 양차이
첫 읽기14,79088213,908
0.2초 안20,63720,286351
이후 10초——114~730

첫 읽기에서 차이가 13,908프레임이었습니다. 버퍼 3,528을 훨씬 넘으니 검사는 시작하자마자 녹음을 끊었습니다.

그런데 끊지 않고 계속 읽게 두면 이야기가 달라졌습니다. 0.2초가 되기 전에 차이는 351로 줄었고, 그 뒤 10초 동안 114~730 사이에 머물렀습니다. 모두 버퍼 안입니다. 같은 때 에뮬레이터의 오디오 HAL 로그에는 producerThread was late delivering frames가 남아 있었습니다.

원인: 잃은 입력이 아니라 밀린 입력

시작 직후의 차이는 장치가 앱보다 먼저 잡아 둔 프레임이었습니다. 이 프레임은 사라지지 않았습니다. 앱이 이어서 읽으면 모두 읽혔고, 그래서 차이가 버퍼 안으로 돌아왔습니다. 실제로 잃은 입력은 없었습니다.

“장치 위치가 버퍼 이상 앞섰다면 유실"이라는 판단은 녹음이 안정된 뒤에만 맞습니다. 막 시작한 순간의 일시적인 상태를 같은 기준으로 봐서 오판한 것입니다.

더 문제였던 점은 검사의 목적과 결과가 맞지 않았다는 것입니다. 이 위치가 맞지 않아도 녹음 파일과 서버 채점에는 영향이 없습니다. 실시간 안내라는 부가 기능을 위한 검사가 핵심 기능인 녹음을 끊고 있었습니다.

고친 방법: 녹음은 계속하고, 시각 기준만 쉰다

위치가 읽은 양과 맞지 않아도 녹음을 끊지 않게 바꿨습니다. 맞지 않는 동안에는 그 위치를 실시간 음높이의 시각 기준으로 쓰지 않고, 다시 맞으면 그때 기준을 갱신합니다.

if (captureTimestampAligned(timestamp.framePosition, fileSamples - segmentStart + count, input.bufferSizeInFrames)) {
    segmentNanos = timestamp.nanoTime - timestamp.framePosition * 1_000_000_000 / RATE
    timestampValid = true
    boundary = CaptureBoundary(id, segment, segmentStart, RATE, segmentNanos, true)
} else if (timestampValid) {
    // 녹음은 계속하고, 위치가 다시 맞을 때까지 실시간 음높이의 시각 기준으로 쓰지 않는다.
    timestampValid = false
    boundary = CaptureBoundary(id, segment, segmentStart, RATE, segmentNanos, false)
}

시각 기준이 무효인 동안 나오는 음높이 관측은 ‘분석 불가’로 표시됩니다. 그동안 실시간 음높이 안내만 잠깐 쉬고, 녹음 파일은 그대로 이어서 씁니다. 녹음 구간이 새로 시작될 때도 기준은 무효로 시작해서, 처음으로 위치가 맞는 읽기에서 정해집니다.

판정 조건은 순수 함수로 떼어 냈습니다.

internal fun captureTimestampAligned(framePosition: Long, readFrames: Long, bufferFrames: Int): Boolean =
    framePosition <= readFrames + bufferFrames

함수로 떼어 낸 덕에 기기 없이 측정값 그대로 테스트를 만들 수 있었습니다. 첫 읽기 값(14,790 / 882)은 맞지 않음, 줄어든 뒤의 값(20,637 / 20,286)은 맞음으로 나와야 합니다. 버퍼 경계 바로 안과 바로 밖도 함께 검사합니다.

확인한 결과와 한계

  • 고친 뒤 에뮬레이터에서 0:30 길이 곡의 평가 녹음이 끝까지 진행되어 ‘연주를 마쳤어요’가 떴습니다.
  • Android 호스트 테스트 1,041개가 실패 없이 통과했습니다.
  • 실기기에서는 확인하지 않았습니다. 시작 직후 차이가 실기기에서 얼마인지, 실시간 음높이 안내가 얼마 동안 쉬는지는 모릅니다.
  • 측정은 에뮬레이터 한 대, 한 곡의 녹음 기록입니다. 시작 직후 밀린 양이 기기와 오디오 경로마다 얼마나 다른지는 측정하지 않았습니다.

남은 과제

  • 실기기 측정. 같은 임시 로그로 실제 휴대폰에서 시작 직후 차이를 재 보려고 합니다. 차이가 크면 실시간 안내가 첫 음을 놓칠 수 있습니다.
  • 한 음씩 연습과의 관계. 같은 녹음기를 쓰는 한 음씩 연습 판정은 ‘분석 불가’ 창을 끊김으로 봅니다. 시작 직후 시각 기준이 쉬는 구간이 첫 음 판정을 늦추는지는 따로 확인하지 않았습니다.
  • 진짜 유실 감지. 이번 수정 뒤에는 녹음이 안정된 뒤 실제로 입력을 잃더라도 녹음은 끊기지 않고 실시간 기준만 쉽니다. 이 경우를 따로 알리거나 기록해야 할지는 아직 정하지 않았습니다.

이번 일에서 남긴 교훈은 두 가지입니다. 이상 신호를 ‘에뮬레이터라서’로 넘기기 전에 값을 한 번 재 볼 것, 그리고 부가 기능의 검사가 핵심 기능을 멈출 수 있는 구조인지 확인할 것입니다.
